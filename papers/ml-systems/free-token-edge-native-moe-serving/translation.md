# FreeToken: 高效的边缘原生 MoE 服务与带宽自适应执行（FreeToken: Efficient Edge-Native MoE Serving with Bandwidth-Adaptive Execution）

**作者**: Shuo Yang, Xiaoze Fan, Melissa Pan, Haocheng Xi, Zhe Wang, Shanlin Sun, Kurt Keutzer, Song Han, Matei Zaharia, Chenfeng Xu, Ion Stoica
**翻译日期**: 2026-08-22

---

## 摘要（Abstract）

前沿的开放权重模型越来越容易获得，但服务它们仍然主要依赖数据中心基础设施。我们提出了 FreeToken，一个边缘原生的混合专家（Mixture of Experts, MoE）服务系统，它将个人机器视为一个统一的、弹性的推理平台，而不仅仅是一个小型 GPU。FreeToken 协同设计了完整的服务栈，包括模型布局与加载、专家驻留、CPU–GPU 执行、智能体状态复用以及运行时内存管理，围绕本地 AI 的两个现实：智能体工作负载不断变化其执行模式，而边缘硬件暴露的异构资源其平衡因机器而异。FreeToken 不采用固定的卸载策略，而是持续将计算和模型状态映射到实际可用的资源上。FreeToken 支持超过 20 种 MoE 模型以及真实的编码和工具使用智能体，硬件范围从 8GB 笔记本电脑 GPU 到单个工作站 GPU。更重要的是，它改变了这些机器实际可以服务的模型规模，从笔记本电脑上的 35B 模型到游戏桌面电脑上的 284B 模型，以及单个工作站 GPU 上的 753B GLM-5.2。FreeToken 将开放权重转化为可部署的本地软件，使用户已拥有的机器成为前沿规模智能的实用平台。我们在 http://flashml.ai 发布了该系统。

## 1. 引言（Introduction）

最近的开放权重模型，如 Kimi-K3（Kimi Team, 2026）、GLM-5.2（Z.ai, 2026）和 DeepSeek-V4-Flash-0731（DeepSeek-AI, 2026），正在迅速缩小与最强专有系统的能力差距。然而，发布模型参数只决定了谁能获得模型，而不是谁能负担得起运行它。前沿开放模型仍然依赖于稀缺的数据中心级 GPU 集群，这些集群可能耗资数百万美元，尽管托管 API 可能比类似的专有产品更便宜，但持续使用仍然昂贵。随着智能体应用急剧增加推理需求（Presenc AI Research, 2026; Anthropic, 2026），这种成本对个人用户和小团队来说尤其沉重。因此，开放模型与专有模型之间的能力差距，比那些能够获得前沿模型的人与能够大规模使用它们的人之间的可及性差距，缩小得更快。

乍一看，这种可及性差距似乎是一个硬件问题。然而，超过一亿台消费级机器已经包含独立 GPU，涵盖游戏桌面电脑、工作站和高性能笔记本电脑。* 仅 Steam 就报告了超过 2 亿月活跃用户，其中约 72% 的被调查系统包含独立 NVIDIA GPU（Simon Carless (GameDiscoverCo)，由 gHacks 报道，2026；Valve Corporation, 2026）。总的来说，这些机器代表了一个庞大但未被充分利用的计算资源池。因此，缺失的不是硬件本身，而是一个能够将每台异构消费级机器视为统一推理平台，并自动将其 GPU、CPU、内存和互连资源映射到其能高效运行的最强模型配置的服务系统。

MoE 架构为在边缘设备上服务前沿规模的开放权重模型开辟了一条新途径。一个 MoE 层包含数百个专家，但每个 token 只路由通过其中一小部分。例如，DeepSeek-V4-Flash 在其 43 层中的每一层激活 256 个路由专家中的 6 个，因此其 284B 参数中只有 13B 参与任何单个 token。在部署精度下，这个活跃参数占用量适合 RTX 5090 的 32GB 内存容量。然而，稀疏性减少了每个 token 的计算量，但没有按比例减少完整专家池所需的内存。整个模型可能仍然远超 GPU 内存，迫使不活跃的专家驻留在主机内存或二级存储中，并按需进入执行路径。因此，MoE 为个人硬件上的前沿推理创造了机会和核心系统挑战：稀疏激活使计算可行，而完整的专家池使高效服务变得困难。

一个不断增长的服务系统生态系统已开始将强大的开放权重模型带到个人硬件上，包括 llama.cpp（Gerganov et al., 2023）、KTransformers（KVCache-AI Team, 2025）和 Ollama（Ollama Team, 2023）。然而，这些现有系统只解决了边缘 MoE 服务问题的片段，并在三个维度上存在不足，阻碍了边缘服务达到其理论容量：

首先，预填充（prefill）很大程度上破坏了 MoE 中工作集的稀疏性。尽管每个 token 只激活少数专家，但长 prompt 中路由的并集通常覆盖每一层中的大多数专家，使专家工作集有效地变得密集。这带来了计算和内存移动方面的挑战，因为超过 VRAM 的专家必须从主机内存中重复流式传输。这个问题在智能体工具调用工作负载中尤其严重，因为长且不断增长的上下文会触发频繁的预填充；然而，现有的边缘服务系统几乎没有提供隐藏专家移动或跨轮次复用循环状态的支持。

其次，解码（decode）呈现相反的情况：每个 token 只激活稀疏的专家子集，但缓存未命中要求专家从主机内存中重复加载、驱逐或执行。现有系统缺乏处理这些未命中的原则性策略。静态放置无法跟随 token 级别的路由变化，而预测和预取可能降低未命中率，但无法决定不可避免的未命中应在 PCIe 传输、GPU 执行和直接 CPU 执行之间如何分配。

第三，这两个问题因边缘资源的多样性和可变性而放大。与数据中心部署不同，消费级硬件在 GPU 容量、PCIe 带宽、主机内存带宽、CPU 能力和可用 VRAM 方面差异很大。这些资源也很少专门用于模型服务：用户可能同时运行浏览器、游戏和其他应用程序，导致可用内存和计算预算随时间波动。因此，没有单一的静态放置或调度策略能够在不同设备、工作负载阶段和变化的运行时条件下都表现良好。

我们提出了 FreeToken，一个建立在两个执行原则和一个弹性资源管理策略之上的系统。（1）带宽自适应执行（Bandwidth-adaptive execution）将有限的边缘带宽从固定瓶颈转变为运行时调度信号。在预填充期间，FreeToken 通过双缓冲（double-buffering）将专家移动与计算重叠：当 GPU 评估当前层时，下一层的专家通过 PCIe 流式传输。解码需要更精细的分配，因为 PCIe 传输和直接 CPU 专家执行都使用相同的主机内存带宽。因此，FreeToken 应用 $q^{\\star}$ 策略，将每个步骤的缓存未命中在 GPU 缓存填充和直接 CPU 执行之间分配（§ 3.2），匹配部署机器能维持的带宽。（2）语义感知缓存（Semantic-aware caching）决定了在稀缺内存中保留什么。跨智能体轮次，智能体框架在语义边界（如思考片段和工具调用）编辑上下文。在预填充期间，FreeToken 在这些边界锚定循环状态检查点，以便在编辑后只重新计算新的后缀。在解码期间，相邻 token 通常路由到重叠的专家。FreeToken 通过共享 LRU 专家缓存捕获这种 token 间路由局部性，允许大多数路由访问在 VRAM 中命中，只将剩余的未命中留给 $q^{\\star}$ 策略。（3）弹性边缘资源管理（Elastic edge resource management）使 FreeToken 适应个人硬件不断变化的内存条件。在调度器安全点，FreeToken 动态调整 GPU 专家缓存的大小并在修订的内存预算下重建，无需重启引擎或重新加载主机驻留的专家池。FreeToken 进一步通过将专家直接加载到其最终主机布局中，然后再固定已填充的内存，来减少启动延迟。

FreeToken 支持超过 20 种 MoE 模型，涵盖广泛的消费级和工作站级硬件。在实验部分，我们主要评估 FreeToken 在三个代表性前沿模型上：Qwen3.6-35B-A3B、DeepSeek-V4-Flash 和 GLM-5.2；六台机器，从 8 GB RTX 4060 笔记本电脑到单个 RTX PRO 6000 工作站；使用四个真实智能体工作负载；并与 llama.cpp、Ollama、KTransformers 和 MoE-Infinity 进行比较。具体来说，在 RTX 5090 上，FreeToken 在 Qwen3.6-35B-A3B 上维持 77–83 tok/s，在 DeepSeek-V4-Flash 上维持 22–25 tok/s，在所有工作负载上比最先进的边缘服务高出 1.5–2.3 倍。其性能在工作负载变得越来越智能体化时也保持显著稳定：解码速率保持在单轮设置的 12% 以内，而竞争系统则显著下降。优势在尾部延迟中更为明显。FreeToken 在每个工作负载中将最坏情况 TTFT（首 token 时间）保持在 44 秒以下，而每个基线在至少一个设置中超过 150 秒——这足以在真实智能体客户端中触发超时。在五个消费级系统中，FreeToken 将解码吞吐量提高了 1.3–2.1 倍。在 8 GB RTX 4060 笔记本电脑上，它以 39.3 tok/s 的速度服务 35B 模型，超过了 Codex 的 33 tok/s 中位解码速度。在 32 GB 游戏桌面电脑上，它交互式地服务 284B 模型。在单个 RTX PRO 6000 工作站 GPU 上，它以 llama.cpp 两倍的吞吐量服务 753B GLM-5.2。

总之，这些进步将开放权重转化为开放访问，将前沿智能从数据中心基础设施带到用户已拥有的机器上。FreeToken 推动了本地推理的速度和能力前沿，使个人硬件能够交互式地服务以前只有在数据中心才实用的模型。我们在 flashml.ai 发布了该系统。

## 2. 边缘 MoE 服务的挑战（Challenges in Edge MoE Serving）

MoE 是边缘服务的自然架构。一个典型的 MoE 层存储 $E$ 个专家，但每个 token 只路由通过 $k \ll E$ 个，因此单个解码步骤触及的权重只是层总参数的一小部分。然而，在实践中，现有的边缘服务引擎（Gerganov et al., 2023; KVCache-AI Team, 2025; Xue et al., 2024）远未达到硬件理论支持的能力，而且在智能体工作负载上这种不足更为严重：首 token 时间（TTFT）随每次工具调用而增长，解码速度远低于机器的内存带宽。本节探讨了这种不足背后的三个挑战：预填充成本（§ 2.1）、解码成本（§ 2.2）以及两者之下的资源可变性（§ 2.3）；§ 3 的三个小节依次回答了它们。

### 2.1 预填充阶段的挑战：传输和重复计算成本（Challenges in the Prefill Stage: Transfer and Recomputation Costs）

预填充决定了每个智能体轮次的 TTFT。在边缘硬件上，预填充时间主要由两部分组成：专家传输，其规模与整个模型而非激活路径相关；以及上下文重计算，智能体会话触发的频率远高于当前系统所能承受的。

专家传输在每次预填充上增加了数秒。尽管解码将每个 token 路由到仅 $k$ 个专家，但预填充过程涉及每层数千个 token。结果，这些路由 token 激活了几乎整个专家集。因此，预填充过程几乎通过 CPU–GPU 互连流式传输完整的专家池。这引入了严重的 I/O 开销，而 VRAM 常驻部署则完全不会执行此操作。以 DeepSeek-V4-Flash 的 FP4 部署为例，它需要传输大约 140 GB 的专家权重，在 RTX 5090 系统（PCIe 5.0 x16，~60 GB/s）上增加大约两秒，在 RTX 4090 和 3090 级桌面电脑（PCIe 4.0 x16，~25 GB/s）上增加五秒，在笔记本电脑常见的 x8 链路上增加十秒或更长时间。按需获取专家的引擎会将整个窗口暴露为 GPU 空闲时间。这种多秒延迟在智能体服务中通常是不可接受的。

智能体工具调用触发频繁的重新预填充。第二个挑战是重复模型已完成工作的计算。许多前沿模型采用混合注意力架构，将全注意力与滑动窗口注意力交错（例如 DeepSeek-V4-Flash (DeepSeek-AI, 2026) 和 GPT-OSS (OpenAI, 2025)）或循环层（例如 Qwen3.6-35B-A3B 中的门控 DeltaNet (Yang et al., 2024b) 和 Kimi-K3 中的 Kimi Delta Attention (Kimi Team, 2025)）。与标准注意力不同，这些层将过去的上下文压缩为单个状态或最近的 KV 条目窗口。因为每个保存的状态消耗的内存与数百个 token 的 KV 缓存一样多，服务引擎只保留少量检查点。智能体工作负载几乎在每个轮次修改上下文。例如，工具调用经常删除旧输出和思考片段。由于这些修改，任何在修改位置之后获取的检查点都会失效。引擎必须回退到修改前的最后一个有效检查点。由于检查点稀疏，引擎通常不得不重新预填充数千个 token。然而，消费级 GPU 无法隐藏这种重复成本：RTX 5090 的密集 BF16 吞吐量大约是 H100 的五分之一，是 B200 的十分之一，因此每次长上下文的冗余重新预填充都会占用 GPU 数十秒。

### 2.2 解码阶段的挑战：缓存未命中和有限的 CPU 带宽（Challenges in the Decode Stage: Cache Misses and Limited CPU Bandwidth）

解码延迟取决于每个步骤未命中专家的服务方式，我们的分析将现有引擎的减速归因于两个硬件特征和一个策略后果：静态专家放置错过了大部分路由流量，消费级 CPU 带宽太小无法单独吸收剩余部分，而未命中工作在两条路径之间的正确分配取决于具体硬件。

静态专家放置错过了路由流量。现有混合引擎在加载或预填充时固定其专家放置：llama.cpp 在加载模型时将 MoE 张量分配给设备（Gerganov et al., 2023），KTransformers 将“热”专家子集固定在 GPU 内存中，其余在 CPU 上执行（KVCache-AI Team, 2025）。然而，路由随每个 token 和每个工作负载而变化。在预填充时冻结的放置只捕获了路由流量的一小部分。结果，大部分专家评估落在 CPU 上，导致 GPU 和 PCIe 链路都空闲（§ 5.3）。

消费级 CPU 无法单独承担解码。在小批量解码时，专家执行是内存绑定的：每个 token 流式传输一次路由专家权重。消费级平台将 CPU 连接到两个 DRAM 通道。这为双通道 DDR4 提供大约 50 GB/s 的峰值带宽，为 DDR5 提供 80-90 GB/s，而单个 RTX 4090 或 5090 从其封装内存中抽取 1-1.8 TB/s。由于这种带宽差距，纯 CPU 专家路径将解码速度限制在相同权重从 VRAM 维持速度的一小部分，无论有多少核心可用。

工作的正确分配取决于具体硬件。未命中的专家可以通过 PCIe 传输并在 GPU 上执行，也可以在 CPU 上执行其权重所在的位置。两种方法都不是普遍可取的。仅依赖传输会在主机内存能提供比链路移动更多字节时，让剩余的主机带宽和 CPU 核心空闲。相反，仅依赖 CPU 执行会让 PCIe 链路空闲，并放弃缓存填充带来的未来命中。正确的混合取决于硬件。例如，使用 LPDDR5 的 RTX 4060 笔记本电脑和使用 DDR5 的 RTX 5090 桌面电脑处于主机到 PCIe 平衡的两端。这种最优混合无法从规格表中读取。因此，快速设计必须在实际运行的机器上定量地做出这种分配。

### 2.3 资源管理的挑战：边缘没有专用资源（Challenges in Resource Management: Nothing on the Edge Is Dedicated）

在数据中心环境中，GPU 和 CPU 资源通常完全专用于服务工作负载。然而，在笔记本电脑和个人电脑等边缘设备上，LLM 服务只是众多并发应用程序之一。因此，服务引擎可用的资源是高度动态的。

VRAM 预算及其分配在服务期间频繁变化。在边缘设备上，GPU 与桌面合成器、浏览器和游戏共享，每个都可能随时占用数 GB 的 VRAM。因此，服务引擎可用的预算在不同启动之间不同，并且在服务期间随时可能缩小或增长。该预算的最佳分配也会移动：智能体会话跨轮次累积上下文，因此 KV 缓存需求增长，而专家工作集大致保持固定，在第一轮选择的分配在许多轮次后就错了。因此，GPU 内存必须在运行时保持可调整，包括总大小以及在 KV 缓存和专家之间的分配，无需重启引擎。

引擎启动慢，而且经常发生。启动服务引擎是资源密集型的：完整的专家池必须从磁盘加载，GPU 必须在第一个请求之前预热。对于 DeepSeek-V4-Flash 的 FP4 部署，仅从 7 GB/s NVMe 驱动器读取大约 140 GB 的池就需要大约 20 秒，然后才开始任何预热。在边缘机器上，这种成本会重复：用户在需要时打开引擎，关闭以释放机器，切换到不同模型也会重启引擎。因此，边缘引擎必须快速启动。

## 3. FreeToken 设计（FreeToken Design）

FreeToken 围绕两级专家内存层次结构组织边缘 MoE 服务（图 2）。CPU 驻留的专家池持有完整的路由专家权重并保持真实数据源，而非专家权重则驻留在 GPU 上。FreeToken 将剩余的 GPU 内存转变为一个由所有 MoE 层共享的弹性专家缓存：每个槽位持有评估一个层-专家对所需的所有张量，因此驻留、查找和执行都在逻辑（层，专家）标识符上操作，而非张量分片。

设计遵循了 § 2 确定的两个服务阶段的瓶颈。在预填充期间（§ 3.1），FreeToken 将大量的专家移动隐藏在计算之后，并维护能够承受智能体上下文编辑的前缀（包括循环状态）。在解码期间（§ 3.2），带宽自适应执行根据机器的两个测量带宽，在 PCIe 传输和 CPU 执行之间划分缓存未命中。在这两个阶段之下，弹性专家内存生命周期（§ 3.3）将 GPU 缓存容量转变为运行时可调整的资源，而非加载时的常量。

### 3.1 预填充协同设计：流水线加载和语义感知状态缓存（Prefill Codesign: Pipelined Loading and Semantic-Aware State Caching）

§ 2.1 将预填充成本归因于两个组成部分：大量的专家传输和冗余重计算。FreeToken 用专用机制回答了每一个：全层双缓冲将前者隐藏在计算之后，语义感知状态缓存让前缀（包括循环状态）能够承受原本会触发后者的上下文编辑。

全层双缓冲将传输隐藏在计算之后。因为预填充激活了每一层的几乎整个专家集（§ 2.1），FreeToken 不按需获取预填充专家。它从全局槽位池分配两个全层缓冲区。当 GPU 从一个缓冲区计算层 $l$ 的路由专家时，一个专用传输流同时将层 $l+1$ 的完整专家集加载到另一个缓冲区。通过加载整个层，传输甚至可以在该层的路由已知之前开始。这确保了权重移动在后台连续进行，而非在层之间串行。然后缓冲区交换角色。因为它们共享解码缓存的槽位池，所以没有单独的预填充缓存，也没有阶段交接，从预填充中存活下来的条目为延迟敏感的解码阶段提供了种子。当槽位池无法腾出两个完整层时，FreeToken 回退到按需预填充加载，而不是过度订阅 GPU 内存。

语义锚点在上下文编辑中保留循环状态。混合注意力模型在 KV 缓存之外增加了第二种前缀资源。FreeToken 使用基数前缀树（radix prefix tree）管理全注意力 KV，遵循现有服务系统（Zheng et al., 2024）；然而，循环层将其整个前缀压缩为一个不断演化的状态，无法部分重用，因此这些层的前缀重用依赖于在预填充和解码期间获取的状态检查点。为此，FreeToken 维护了一个语义感知状态缓存。这是一个附加到前缀树节点的循环状态检查点小池。当新请求到达时，它从位置在 prompt 编辑后仍然存活的最深检查点恢复。因为每个检查点捕获了所有此类层的完整循环状态，所以只能持有少量，它们的位置决定了它们的价值。

FreeToken 在语义锚点处花费这个预算：标记思考片段、工具调用和输出以及对话轮次的特殊 token 边界。这些正是智能体框架修改和截断上下文的位置：OpenClaw 从每个助手轮次中剥离思考块，除了最新的（OpenClaw Contributors, 2026）；OpenCode 将超出最近窗口的工具输出替换为固定占位符（OpenCode, 2026）；SWE-agent 省略除最后 $n$ 个观察之外的所有内容（Yang et al., 2024a）。在每种情况下，编辑都替换或删除由特殊标记标记的整个块，例如思考片段、工具调用、工具输出和对话轮次。因为框架保留了直到编辑块的确切前缀，在这些语义边界获取的检查点比放置在任意位置的检查点更有可能在这次截断中存活。当智能体框架在工具调用后编辑历史时，保留的前缀在此类边界处结束。锚定在那里的检查点让全注意力层重用其 KV 缓存直到编辑点，而循环层从锚点恢复，因此只有真正新的后缀被重新预填充。检查点槽位通过 LRU 驱逐回收，独立于 KV 池。

### 3.2 解码协同设计：语义感知专家缓存和 $q^{\\star}$ 策略（Decode Codesign: Semantic-Aware Expert Caching and q⋆ Policy）

在解码期间的每个 MoE 层，路由器和缓存查找在 GPU 上运行，并识别已驻留在缓存中的活跃专家 $\\mathcal{H}$，这些专家直接在 GPU 上执行。剩下的挑战是如何服务 $m$ 个唯一未命中的专家 $\\mathcal{M}$。

语义感知专家缓存跟随模型不断演化的计算。在解码期间，路由表现出强烈的时间专家局部性：在连续步骤中，相同的 MoE 层重复路由到重叠或最近使用的专家，这种路由一致性已在跨模型系列中测量（Liang et al., 2025）。FreeToken 通过语义感知专家缓存将这一特性转化为 GPU 驻留。它不是根据加载时选择的工作负载无关放置来固定专家，而是维护一个共享 LRU 驻留空间，其内容持续跟随路由器选择的专家。缓存命中刷新专家的最近使用，缓存填充接纳新选择的专家，驱逐移除模型最近最少使用的专家。通过这种方式，稀缺的 GPU 内存跟踪当前生成的工作集。§ 5.3 在我们的智能体跟踪上确认了这种局部性，并量化了其在相同缓存容量下相对于静态放置的优势。

缓存无法消除未命中：冷启动、工作集突然转移和有限容量仍然使一些选择的专家无法进入 GPU。带宽自适应执行服务这些残余未命中，决定将哪些专家带入缓存，哪些在 CPU 上原地执行。

测量的带宽决定了未命中的服务方式。FreeToken 的带宽自适应执行根据两个测量带宽的平衡，动态将 $m$ 个未命中专家在 PCIe 传输和 CPU 执行之间分配：固定的专家传输带宽 $B_{\\mathrm{P}}$ 和主机端专家处理带宽 $B_{\\mathrm{H}}$。它将未命中划分为缓存填充集 $\\mathcal{F}$ 和 CPU 执行集 $\\mathcal{C}$：

$$\\mathcal{M} = \\mathcal{F} \\dot{\\cup} \\mathcal{C}, \\qquad q = |\\mathcal{F}|. \\tag{1}$$

$\\mathcal{F}$ 中的专家被传输到缓存槽位，在 GPU 上执行，并保留供将来重用；$\\mathcal{C}$ 中的专家直接从 CPU 驻留的专家池执行，驻留状态不变。这两个集合并发服务：缓存填充以全 PCIe 速率进行，而 CPU 仅消耗饱和链路留下的主机带宽，将残余主机带宽转化为当前 token 进度，而不挂起缓存更新。

最优分配比源自残余带宽论证。令 $S$ 表示一个完整专家的大小（以字节为单位）。由于专家 DMA 传输和 CPU 执行都从相同的主机内存子系统读取，饱和的 PCIe 传输留下残余带宽：

$$B_{\\mathrm{R}} = \\max(B_{\\mathrm{H}} - B_{\\mathrm{P}}, 0) \\tag{2}$$

这个残余带宽正是可用于并发 CPU 专家执行的。因此，两个分支的执行时间为：

$$T_{\\mathrm{fill}}(q) \\approx \\frac{q S}{B_{\\mathrm{P}}}, \\qquad T_{\\mathrm{cpu}}(m - q) \\approx \\frac{(m - q) S}{B_{\\mathrm{H}} - B_{\\mathrm{P}}}. \\tag{3}$$

平衡并发分支得到：

$$\\frac{q}{m - q} \\approx \\frac{B_{\\mathrm{P}}}{B_{\\mathrm{H}} - B_{\\mathrm{P}}}, \\qquad q^{\\star} \\approx m \\frac{B_{\\mathrm{P}}}{B_{\\mathrm{H}}}. \\tag{4}$$

这个单一公式涵盖了所有硬件平衡。当 $B_{\\mathrm{H}}$ 接近 $B_{\\mathrm{P}}$ 时，$q^{\\star}$ 接近总未命中数 $m$，系统退化为纯按需缓存填充，无需单独的执行分支或策略。

在实践中，FreeToken 将 $q^{\\star}$ 四舍五入为整数，并将 $\\mathcal{F}$ 的具体选择委托给缓存替换策略。它总是保留至少一个填充，因此即使 CPU 处理大多数未命中，缓存也会继续预热。带宽参数（$B_{\\mathrm{H}}$ 和 $B_{\\mathrm{P}}$）在部署时在目标硬件上进行经验分析。在执行期间，CPU 和 GPU 分别计算其部分和并合并它们，保留精确的 MoE 输出，无需算法近似。按执行顺序，FreeToken 首先启动 CPU 分支。然后运行 GPU 未命中路径，该路径包括缓存更新、$\\mathcal{F}$ 的批量复制以及组合 GPU 执行集 $\\mathcal{G} = \\mathcal{H} \\cup \\mathcal{F}$ 的分组评估。同时，CPU 工作者处理 $\\mathcal{C}$。因此，暴露的层延迟是两个并发分支中较慢的那个，这正是方程 4 平衡的量。这个每层控制流包括未命中检测、集大小调整、受害者选择和 CPU 分支本身。将所有这些保持在静态捕获的 CUDA Graph 中是一个自身的实现问题；§ 4.1 介绍了图兼容的缓存和执行机制。

### 3.3 边缘原生运行时的弹性内存管理（Elastic Memory Management for Edge-Native Runtimes）

与数据中心部署不同，边缘 GPU 资源很少专门用于 LLM 服务。服务引擎可用的 VRAM 可能在不同启动之间波动，甚至在会话中途发生变化，因为 GPU 与其他应用程序共享。此外，随着上下文增长，内存需求本身在专家缓存和 KV 缓存之间转移，引擎通常按需启动。因此，从磁盘构建 CPU 驻留的专家池是用户可见的成本。FreeToken 通过两种机制吸收这种可变性，这两种机制都依赖于一个属性：因为 CPU 驻留的专家池保持为真实数据源，GPU 内存只影响性能，从不影响正确性。

运行时缓存重配置。在分配非专家权重和运行时状态后，FreeToken 将剩余的 GPU 内存预算在 KV 缓存页和完整专家槽位之间分配。这种分配不是在启动时固定的。在任何调度器安全点，FreeToken 可以为修订的运行时 VRAM 预算重建 GPU 专家缓存。这是在不重启引擎或重新加载 CPU 驻留专家池的情况下完成的，动态地为新的缓存配置重新建立捕获的执行路径。

快速引擎启动。启动时间有两个组成部分：将专家池从磁盘加载到主机内存，以及传统上在服务之前预热 GPU。FreeToken 缩短了第一个并消除了第二个。加载直接将专家权重从磁盘读取到其最终主机布局中，只有在填充后才固定内存；首先固定空缓冲区只会导致数千页被清零，只是为了覆盖它们。预热在设计上是不必要的：第一个请求使用冷缓存服务，其未命中由 § 3.2 的普通解码路径处理，缓存通过正常服务预热。

## 4. 实现（Implementation）

FreeToken 遵循由 SGLang 和 vLLM 等系统建立的以 GPU 为中心的服务架构（Zheng et al., 2024; Kwon et al., 2023），将分页 KV 缓存管理和基于基数的前缀重用与社区内核库（包括 FlashInfer (Ye et al., 2025) 和 Flash Linear Attention (Yang and Zhang, 2024)）相结合。在这个基础上，两个实现层实现了 § 3 的设计：图兼容的专家缓存（§ 4.1）及其下的存储和平台机制（§ 4.2）。

### 4.1 CUDA 图兼容的 LRU 缓存（CUDA-Graph-Compatible LRU Cache）

专家缓存本质上是动态的：未命中的具体专家、获取的专家数量以及驱逐的槽位都在每个步骤变化。因此，主机控制的缓存会在每个 MoE 层重新引入昂贵的设备同步。为避免这种情况，FreeToken 将所有依赖于路由的控制严格保持在 GPU 上。这种动态控制表示为静态捕获图中的数据。具体来说，该数据由固定形状的工作缓冲区和设备驻留的有效计数组成。

设备端缓存控制。对于每个 MoE 层，一个 GPU 内核对路由专家进行去重，根据驻留表对其进行分类，推导基于带宽的获取计数 $q$，选择驱逐受害者，并将逻辑路由 ID 重写为物理槽位 ID 或特殊的 CPU 分配标志。受害者选择避免了经典 LRU 陷阱，即每个驱逐槽位需要一次完整的缓存扫描。相反，单遍内核一次识别 $K$ 个最近最少使用的候选槽位用于驱逐。然后未命中路径简单地消耗前 $q \\le K$ 个这些槽位。结果，受害者发现始终恰好花费一次遍历，与实现的未命中数无关。生成的复制工作列表驱动单个融合传输。因为每个专家库共享相同的逻辑专家到槽位映射（§ 4.2），所以单个设备驻留源/目标索引列表可以在一次固定形状启动中应用于所有库。有效计数用于屏蔽任何未使用的工作。这种设计产生很少的内核启动、高 PCIe 利用率，并从主机移除依赖于路由的决策开销。

图驻留 CPU 执行。带宽自适应执行的 CPU 分支被捕获到同一个图中。对于每个支持的解码批量大小，FreeToken 准备稳定的固定 I/O 缓冲区和持久任务描述符。设备到主机的副本、主机函数提交节点、并发 GPU 路径、同步节点以及主机到设备的结果副本都被捕获在一起。结果，重放重新执行完整的异构步骤，而无需每 token Python 调度。工作者本身形成一个固定到物理核心的持久 C++ 池。它们的内核使用特定于架构的 SIMD 和内核内反量化来消耗专家权重，这保持了路径的带宽受限。最后，它们返回门控加权的每 token 部分输出。

### 4.2 专家存储和平台适配（Expert Storage and Platform Adaptation）

专家库和 FTW 格式。FreeToken 将模型特定的检查点布局规范化为一小批专家库。每个库使用展平的层-专家标识符 $lE + e$ 作为其主维度。所有库中具有相同标识符的行共同构成一个完整的专家。结果，GPU 内核和 CPU 执行器共享一个逻辑专家标识符，无论底层物理格式如何。为了使加载快速，FreeToken 提供了 FreeToken Weight (FTW) 格式，该格式预先将专家权重合并到这种运行时库布局中。在引擎启动期间，此格式允许系统完全跳过张量发现和重新打包。相反，它使用并行直接 I/O 读取对齐的块，直接进入精确大小的主机库，这些库仅在填充后才固定（§ 3.3）。

平台适配。在加载时，FreeToken 选择与专家表示、GPU 架构和 CUDA 环境兼容的 GPU 内核。同时，CPU 执行器分派到可用的 SIMD 实现和物理核心布局。当完整的专家池无法被固定或注册用于 DMA（这是某些操作系统和驱动程序配置的限制）时，FreeToken 回退到纯 CPU MoE 后端。在此后端下，专家权重保留在可分页的主机存储中，所有路由专家在 CPU 上执行。非专家层保留在 GPU 上，只有激活大小的输入、路由元数据和聚合输出跨越 CPU-GPU 边界。这条路径以峰值传输带宽为代价，换取了在无法建立快速路径的平台上的可部署性。

## 5. 评估（Evaluation）

我们在真实智能体工作负载上评估 FreeToken，服务完整专家池超过 VRAM 的 MoE 模型，与六台机器上积极维护的边缘服务引擎进行比较。§ 5.1 详细说明了设置，§ 5.2 报告了主要端到端结果，§ 5.3 将收益归因于 FreeToken 的机制并测试其跨硬件的通用性。

### 5.1 实验设置（Experimental Setup）

硬件。六个独立 GPU 系统（表 1）：五台消费级机器覆盖当前边缘硬件的有效主机和 PCIe 带宽范围，以及一台工作站级机器（单个 RTX PRO 6000 Blackwell, 96 GB）托管前沿规模演示。3090、4090 和 5090 系统是租用的双插槽服务器，其 CPU 远超任何边缘主机，因此其上的每次服务运行和带宽测量都限制为 6 个 CPU 线程并固定到 GPU 的 NUMA 节点。通过这种限制，服务器提供 56.7–77.3 GB/s 的主机带宽，与两台真实边缘机器在自然满线程下达到的规模相同（桌面 16 核为 53.8 GB/s，笔记本 14 核为 47.5 GB/s）；桌面和笔记本未分层运行，并在真实边缘硬件上验证了模拟。表 1 中的所有带宽都在部署的张量形状上测量，而非来自平台规格。

模型。两个 MoE 模型：DeepSeek-V4-Flash（284B 参数，13B 活跃）（DeepSeek-AI, 2026），从官方检查点服务，其路由专家原生 MXFP4 量化；以及 Qwen3.6-35B-A3B（Qwen Team, 2026）BF16，在所有引擎中提供精确精度对等（8GB 笔记本服务其官方 NVFP4 版本（NVIDIA, 2026b））。跨硬件研究增加了 GLM-5.2（Z.ai, 2026）（753B 参数，40B 活跃；NVFP4 路由专家（NVIDIA, 2026a），433 GB 检查点），由 RTX PRO 6000 作为前沿规模层服务。

工作负载。四个智能体场景。W1，数学推理：AIME 竞赛问题，使用长链式解码回答，无工具使用——单轮且解码主导。W2，编码智能体：通过 OpenCode 框架解决的 SWE-bench 仓库问题，包含真实工具执行，跨三个脚本化用户轮次。W3，编码智能体，原生协议：相同问题由 Claude Code 通过每个引擎的 Anthropic 兼容端点驱动，该端点生成并发请求的子代理并将会话增长到 56–65k token。W4，邮件/日历智能体：通过 OpenClaw 在默认配置下（其 120 秒空闲看门狗被禁用，以便慢速引擎仍可测量）的邮箱套件上进行十三个固定用户轮次，携带约 24.5k token 的系统上下文基线。所有引擎服务相同的框架和相同的请求；编码运行必须产生参考黄金补丁，W4 运行必须完成所有十三个轮次。

基线。llama.cpp、Ollama、KTransformers 和 MoE-Infinity（Xue et al., 2024）在其支持的配置上。权重格式完全对齐：每个引擎以 BF16 服务 Qwen3.6，每个引擎以比特精确方式消耗 DSV4-Flash 的原生 MXFP4 专家块。

指标。解码吞吐量（每请求平均 tok/s）和 TTFT（每请求平均）。智能体轨迹在引擎间发散，因此不比较跨引擎的挂钟时间总数。

### 5.2 主要结果（Main Results）

图 3 报告了两个模型在所有四个工作负载上每个引擎的解码吞吐量和平均 TTFT（RTX 5090；Qwen3.6 使用 6 CPU 线程，DSV4-Flash 使用 8）。

解码吞吐量。FreeToken 在 Qwen3.6 上维持 77–83 tok/s，在 DSV4-Flash 上维持 22–25 tok/s，分别是每个工作负载中最强基线的 1.8–2.3 倍和 1.5–1.9 倍。在智能体服务下速率也保持稳定：在三个智能体工作负载中保持在单轮 W1 值的 12% 以内，而最敏感于上下文的基线 KTransformers 在 DSV4-Flash 上在 W2 时已失去其 W1 速率的 31%。单流基准测试因此高估了基线智能体性能。MoE-Infinity 仅服务 W1（8.8 tok/s）：其每专家预填充暂存上限中止了更长 prompt 的工作负载，其捆绑服务器不保留跨请求的 KV 缓存。

首 token 时间。FreeToken 在六个多轮单元中的五个中发布了最低的平均 TTFT（Qwen3.6×W3 有利于 KTransformers 的 GPU 预填充臂），而 W1 的短孤立提示有利于 llama.cpp。尾部比均值更尖锐地分离引擎：FreeToken 的最差轮次在每个单元中保持在 44 秒以下，而每个基线在某个地方超过 150 秒——llama.cpp 为 232 秒，Ollama 为 179 秒，KTransformers 为 946 秒。这些停顿超过了真实客户端放弃请求的阈值：OpenClaw 提供 120 秒空闲看门狗，Claude Code 的默认请求超时约为十分钟。尾部 TTFT 因此是可用性边界，而非延迟统计。

## 6. 相关工作（Related Work）

专家卸载和缓存。服务专家池超过 GPU 内存的 MoE 模型已收敛到 FreeToken 也采用的架构：完整的专家池驻留在主机内存或磁盘上，专家子集缓存在 GPU 上。EdgeMoE（Yi et al., 2023）为设备上推理建立了这种设计；Mixtral-offloading（Eliseev and Mazur, 2023）将 LRU 专家缓存与推测预取相结合；MoE-Infinity（Xue et al., 2024）跟踪请求级激活模式以指导预取和缓存；ProMoE（Song et al., 2024）、ExpertFlow（He et al., 2024）和 FineMoE（Fan et al., 2025）锐化了预测未来路由的预测器。跨 MoE 模型系列的路由一致性测量（Liang et al., 2025; Lin et al., 2025）支持了这种缓存可能有效的前提。这些系统在预测未命中的好坏上有所不同，但在服务方式上没有不同：每个未命中最终都是 PCIe 传输，因此无论预测变得多么准确，解码延迟都受限于链路，而主机计算能力空闲。互补的一条线通过降低保真度来减少传输量：HOBBIT（Tang et al., 2024）获取未命中专家的降低精度副本，SiDA（Du et al., 2024）和 SMoE（Zhu et al., 2025）替换或跳过低分专家（以准确性换取带宽），而 Pre-gated MoE（Hwang et al., 2024）重构和微调路由器本身。FreeToken 保持路由计算精确且模型未修改；它改变残余未命中的服务方式，而非预测的好坏。

混合 CPU-GPU 执行。第二条线将 CPU 作为计算资源而非权重存储。对于密集模型，FlexGen（Sheng et al., 2023）和 DeepSpeed-Inference（Aminabadi et al., 2022）以层粒度流式传输权重，用于面向吞吐量的批量推理，PowerInfer（Song et al., 2023）根据激活统计分割神经元，这需要 ReLU 系列稀疏性和学习的预测器；llama.cpp 和 Ollama（Gerganov et al., 2023; Ollama Team, 2023）在加载时将整层静态分配给设备。对于 MoE，Fiddler（Kamahori et al., 2024）首次将未命中专家视为可以在 CPU 上执行的工作，而不仅仅是移动的数据；KTransformers（KVCache-AI Team, 2025）通过 AMX 优化内核使原地 CPU 专家执行变得快速；HybriMoE（Zhong et al., 2025）通过每步调度模拟重新平衡 CPU/GPU 队列；SMoE（Zhu et al., 2025）使用贪心双指针启发式平衡加载与 CPU 时间；其他系统在 CPU 上执行每个未命中（Huang et al., 2025）或流水线化 CPU、GPU 和 I/O 以用于离线吞吐量（Cao et al., 2024; Fang et al., 2025）。在这一系列中，工作的分配要么在启动时固定（KTransformers 即使在 PCIe 空闲且缓存容量可用时也将路由专家保留在 CPU 上），要么由主机端启发式重新计算，其调度成本和每层同步无法被捕获到 CUDA Graph 中；llama.cpp 同样无法在其混合模式下维护图执行。此外，这些系统围绕单次、短提示推理进行设计和评估，通常使用未量化权重；没有一个提供多轮智能体会话在每次工具调用轮次重新进入预填充时所需的跨请求前缀重用。相反，FreeToken 从两个测量带宽中推导出分配作为闭合形式比率（足够便宜以保持在捕获图内的设备驻留），并将其嵌入服务运行时而非单请求框架。

服务基础设施和分层内存。FreeToken 建立在 vLLM（Kwon et al., 2023）和 SGLang（Zheng et al., 2024）的以 GPU 为中心的服务基础上，以及 FlashInfer（Ye et al., 2025）上，其注意力调度为 CUDA Graph 捕获内的动态行为树立了先例。在内存管理方面，SGLang HiCache（SGLang Team, 2025）将 KV 缓存分层到 GPU、主机和远程存储，以在长多轮会话中保留前缀重用；WiSP（WiSP authors, 2026）通过边际延迟值在专家权重和 KV 缓存之间分割 VRAM；eLLM（eLLM authors, 2025）在运行时重新平衡弹性内存池；FluxMoE（FluxMoE authors, 2026）将专家分页以优先考虑 KV 缓存容量。这些管理器移动被动字节：当页面或专家缺失时，它只能被获取，WiSP 自己的分析发现单流解码受限于 PCIe，无论预测准确性如何，这是仅靠分配无法提升的上限。专家权重提供了一个进一步的自由度，因为缺失的专家也可以在其驻留的地方计算。FreeToken 结合了这两个杠杆：它将分层内存哲学应用于专家池。它使用具有统一预填充/解码驻留的弹性全专家缓存，并在同一服务基础上添加带宽自适应 CPU 协同执行。我们的贡献是集成运行时和测量带宽模型，该模型在其中协调缓存、传输和 CPU 执行。

## 7. 结论（Conclusion）

我们提出了 FreeToken，一个用于个人硬件上前沿规模 MoE 模型的边缘原生服务系统。FreeToken 建立在一个简单的观察之上：一旦稀疏激活使模型计算可行，本地推理就不再是模型是否适合 GPU 的问题，而是系统如何协调机器的问题。因此，FreeToken 将 GPU、CPU、主机内存和互连视为统一的推理平台，使模型状态和执行适应智能体工作负载不断变化的结构及其运行的硬件。FreeToken 涵盖超过 20 种 MoE 模型和从 8GB 笔记本电脑 GPU 到工作站 GPU 的硬件，支持从 35B 到 753B 参数的模型，同时始终优于现有的边缘服务系统。更广泛地说，我们的结果表明，本地 AI 的边界越来越不仅由硬件容量决定，还由组合已可用资源的服务软件决定。FreeToken 向将开放权重转化为开放访问迈出了一步，使个人机器成为前沿规模智能的实用平台。
