# FreeToken: 高效的边缘原生 MoE 服务与带宽自适应执行

## 一句话总结

FreeToken 让个人电脑（从笔记本到工作站）能流畅运行原本需要数据中心才能跑的大模型，通过智能调度 CPU 和 GPU 资源，把模型“拆”到内存和显存放得下的部分。

## 论文要解决的问题

现在开源的大模型越来越强，但跑它们仍然需要昂贵的数据中心 GPU 集群。普通人手里的电脑（游戏本、工作站）虽然也有不错的显卡，但内存和显存太小，根本装不下几百 B 参数的大模型。这就好比你有一辆跑车（GPU 很强），但油箱（显存）太小，加不了几升油（模型参数），车根本跑不远。

现有的边缘推理工具（如 llama.cpp、Ollama）只是简单地把模型一部分放显卡、一部分放内存，但没解决三个核心难题：
1. **预填充慢**：处理长 prompt 时，需要把模型大部分专家从内存搬到显卡，搬运时间太长。
2. **解码卡**：生成每个 token 时，显卡经常找不到需要的专家（缓存未命中），要么等内存搬运，要么让 CPU 干等。
3. **资源忽多忽少**：你电脑的显存会被游戏、浏览器抢走，可用资源时刻在变。

## 核心方法

FreeToken 的核心思路是：**不把电脑看成“小号数据中心”，而是看成一个弹性资源池，根据当前能用的资源，动态决定怎么分工**。它像一个聪明的仓库管理员，知道哪些货（专家）经常用，放在手边（显存）；哪些偶尔用，放在远处架子上（内存），并且根据当前人手（CPU/GPU 带宽）决定是派人去取货（PCIe 搬运）还是直接在架子上处理（CPU 执行）。

具体来说，FreeToken 有三个核心设计：

### 1. 带宽自适应执行（Bandwidth-Adaptive Execution）
- **做什么**：当显卡找不到专家时（缓存未命中），不是只靠 PCIe 搬运，而是根据当前机器的 PCIe 带宽和 CPU 处理带宽，动态决定多少个专家搬过来（GPU 缓存填充），多少个专家直接在 CPU 上算。
- **技术落点**：通过公式 $q^{\star} \approx m \cdot B_{\mathrm{P}} / B_{\mathrm{H}}$ 计算最优分配比例，其中 $m$ 是未命中专家数，$B_{\mathrm{P}}$ 是 PCIe 带宽，$B_{\mathrm{H}}$ 是 CPU 处理带宽。这样两条路同时走，谁都不闲着。

### 2. 语义感知缓存（Semantic-Aware Caching）
- **做什么**：在预填充和解码阶段，根据“语义边界”（比如思考片段、工具调用）来保存和恢复状态，避免重复计算。
- **技术落点**：在预填充时，用双缓冲隐藏搬运时间；在解码时，用 LRU 缓存跟踪最近使用的专家，利用 token 间的路由局部性（相邻 token 经常用到相同专家），让大部分专家命中显存。

### 3. 弹性内存管理（Elastic Memory Management）
- **做什么**：让 GPU 显存分配能动态调整，适应运行时显存被其他程序抢占的情况。
- **技术落点**：在调度器安全点，动态调整 KV 缓存和专家缓存的显存分配比例，无需重启引擎。

## 实验结果

FreeToken 在多种硬件和模型上进行了测试：

- **RTX 5090 桌面**：在 Qwen3.6-35B 上达到 77-83 tok/s，比 llama.cpp、Ollama、KTransformers 快 1.5-2.3 倍。
- **8GB 笔记本 RTX 4060**：能跑 35B 模型，速度 39.3 tok/s，超过 Codex 的 33 tok/s 中位速度。
- **32GB 游戏桌面**：能跑 284B 的 DeepSeek-V4-Flash。
- **单卡 RTX PRO 6000 工作站**：能跑 753B 的 GLM-5.2，速度是 llama.cpp 的两倍。

消融实验显示：
- 流水线预填充在 16k token 时提升 26% 吞吐量。
- 语义感知缓存比静态放置的未命中率低一半以上（RTX 5090 上，Qwen3.6 未命中率 16% vs 41%）。

## 核心价值与影响

1. **技术层面**：首次提出带宽自适应执行，将 PCIe 带宽和 CPU 带宽统一调度，突破了边缘 MoE 服务的性能瓶颈。
2. **实用层面**：让普通用户的个人电脑能交互式运行前沿大模型，降低了使用门槛。
3. **启发层面**：为边缘 AI 服务提供了新范式——不追求固定优化，而是动态适应异构、多变的资源环境。

**一句话说清为什么值得读**：这篇论文展示了如何让普通电脑跑起大模型，是边缘 AI 落地的关键一步。

## 局限与值得思考的问题

1. **作者承认的局限**：FreeToken 目前主要针对 MoE 模型，对于密集模型（Dense Model）的优化有限。
2. **潜在问题**：带宽自适应执行依赖于准确的带宽测量，如果系统负载波动大，测量可能不准。
3. **进一步方向**：可以探索更智能的预取策略，或者结合模型压缩技术进一步减少内存需求。
