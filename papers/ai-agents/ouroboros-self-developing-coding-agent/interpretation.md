# Ouroboros：让 AI 智能体自己改写自己，还得过评审——解读

> 论文：*Ouroboros: A Self-Developing Frontier Coding Agent with Reviewed Core Evolution*（arXiv:2608.08311v2，2026-08-11）
> 作者：Anton Razzhigaev、Andrei Gritsaev、Andrei Kaznacheev、Nikita Dragunov、Roman Yampolskiy、Andrei Kuznetsov（论文还特别注明系统本身 Ouroboros 是"系统贡献者"，不占正式作者名额）

## 3.1 一句话总结

一个允许"自己改自己核心代码"的编程智能体框架，每次修改必须存档、过评审才能生效，还能越用越强——多个权威基准上刷出新纪录。

## 3.2 论文要解决的问题

**背景**：现在评测编程智能体，分数其实是由四样东西共同决定的：基础模型、**执行框架（harness，相当于"脚手架"）**、环境和评分器。模型只决定"聪明程度"，而"怎么给模型喂上下文、怎么调用工具、怎么验证结果、失败了怎么恢复"这些事，全部由框架负责。论文引用了一系列对照研究：**模型固定不变时，换一个框架，准确率、延迟、token 消耗都会有巨大差异**。

**痛点**：绝大多数生产级框架是"一次性设计"——出厂后就被冻结，再也不改。可是模型在快速进步，今天写死的上下文组装方式、工具调用策略，明天就可能过时；而且框架里积累的小 bug、低效路径，永远不会被修掉。

**类比**：想象同一个顶级厨师（模型），被安排进不同的厨房（框架）。厨房 A 的灶台、备菜流程、食材信息一应俱全（好 harness）；厨房 B 的工具乱放、菜谱过期、没有验收流程（差 harness）。同样的厨师，在两个厨房里端出的菜水平差很远。可绝大多数餐厅的做法是：开业时装修一次厨房，之后十年不动。

**之前的人怎么做的**：学界已有"自我演化智能体"研究：Voyager 只积累技能；Live-SWE-agent 任务中造工具；Autogenesis 规定演化接口；Darwin Gödel Machine 让智能体改脚手架。但论文用一张对比表（Table 1）指出：**此前没有任何系统同时做到"能改核心代码 + 变更必须经过可审计版本控制的评审提交 + 真实部署状态"三件事**——要么只能改提示词/工具（表里大量 ✓ 只在这两列），要么改了核心代码但没有评审闸门（Darwin Gödel Machine 那栏"Reviewed commits"是空白）。一句话：**没人敢让智能体改自己的大脑，更没人在改完之后加一道"审批关"再让它生效。**

## 3.3 核心方法

整体思路一句话：**把"框架"从一个静态工具，变成一份有版本、有评审、可回滚的代码库；让智能体像修自己的房子一样，边住边装修，但每次动承重墙都要过审。**

论文提出四大核心贡献，逐一讲：

### 贡献 1：可自我修改、必须过审的框架架构

技术落点：Ouroboros 把系统切成两层——**启动器+监督器（launcher + supervisor）**（负责启动、进程监督、发布、紧急停机）和**可变智能体仓库**（任务循环、工具、提示词、记忆、评审逻辑、基准适配器都在里面）。所有变更走同一条**提交闸门（commit gate）**流水线：

1. **确定性预检**：版本、数据边界、体积健康检查
2. **指纹**：对暂存的 diff 算哈希
3. **评审**：多模型差异评审小组，必须达到法定多数（sub-quorum 不能记为"干净通过"）；max 模式下还有全仓库范围评审
4. **再算一次指纹**：评审期间有人偷偷改过 diff？指纹不匹配，提交立刻中止

评审前后指纹比对，就像编辑把稿子交给三位审稿人之前、之后各自盖一次火漆印——稿子被人偷换一眼就能发现。任何写入都会使先前的评审证据失效（新鲜度绑定在暂存快照上），所以"先过审再生效"不是口号。

### 贡献 2：两种核心演化模式

**模式 A：递归自由演化（recursive free evolution）**——"改进"本身就是一项任务。智能体先审查当前系统，选一个改进点实现它，任务完成后**可以调度下一轮演化任务**，于是形成一串不断延续的受审更新，而不是跑一次就完事。

**模式 B：经验驱动的核心演化（experience-driven core evolution）**——不单独开"改进任务"，改进藏在普通工作里。任务执行、反思、评审拦截、观测插桩、社交反馈都会暴露故障和低效路径；智能体把它们登记为**持久的错误类别（durable error classes）**并提出结构性修复，然后自主决定要不要开工。所有修复走同一个受审提交闸门。

类比：模式 A 像每周专门留一天"给房子做升级改造"；模式 B 像在日常居住中发现"门把手松了""插座位置反人类"，随手记进一个维修本，攒够了就安排一次水电改造——而且每次改造都留档案、能回滚。

### 贡献 3：Hope——161 天的"活体智能体"现场实验

这是论文最有意思的部分，也是"经验驱动演化"的实锤。自 2026 年 2 月至今，一个持续运行的 Ouroboros 实例 **Hope** 横跨七个交互面（网页聊天、语音、Telegram、Discord、Twitter/X、网站评论、邮箱）服务约 3,600 位真实用户、处理了 222,474 条公开消息。关键设计是"**人提建议，智能体拍板**"：用户的批评、功能请求、bug 报告都只是**咨询性信号**，是否动代码由 Hope 自己决定。

论文给了两个完整的"社交反馈→核心修复"案例：
1. 用户发现 Hope 偶尔重复发同一条消息→智能体追踪到重复发送路径→提交了"逐字重复守卫"补丁
2. 深度自我评审任务频繁以"模型不可用"表象中止→智能体自己排查发现是评审包上下文溢出→把上下文组装路径换成"**感知连通性的上下文图集**"（按导入图中心性排序、按服务商校准大小估计）→修复保留高连通性核心文件

截至 2026-08-06：**$110.6K** 模型开销、**79.7B** token、**175,755** 行代码、**227 MB** 记忆工件、**1,085** 次自我修改提交（94.2% 由智能体撰写）、**63.5%** 的近期评审拦截率（意味着超半数自我修改被拦下整改，评审不是走过场）、40 个模式类别/659 次复发。

### 贡献 4：运行安全架构——让护栏在演化压力下依然有效

论文的核心忧患：**能改自己代码、还能自选模型 API 的智能体，有可能通过"正常演化"悄悄扩大自主权**——换一个更强的模型服务商、绕开某个约束，表面上看只是"一次普通配置变更"，代价和风险却完全不一样。所以护栏不能是一次性措施，必须和演化共存：

- **章程（constitution）**：一份始终加载、不可整体改写/删除的规则文档，原则 P0–P4 是受保护核心（连智能体自己都不能删除或降级）。类比真宪法：修宪可以，但"公民基本权利条款"不可修改。P3 甚至规定"想改评审规则本身，得先过计划评审"——防止"管评审的人先被收买"。
- **确定性守卫**：治理文件被普通写入工具保护；公开消息**不能直接调用**提交/重启/shell/身份编辑工具（堵死"提示词一句话就让核心代码变样"的路径）
- **操作员权威**：独立的认证通道承载预算与路由，支出上限在智能体外部（智能体抬不了自己的工资），`/panic` 由监督器在智能体处理之前解析并终止进程树，任何代码、提示词、章程论证都不得拖延或绕过它
- **双重谱系制**：基准活动全部用**冻结的系统快照**（演化关停），Hope 则在一条独立谱线上继续实时演化——要"可复现的成绩"还是要"活系统"，两者互不污染

一句话概括这套架构哲学：**把"被演化的基底"和"决定变更的权威"彻底分离**——前者可以无限演化，后者永远站在系统外面。

## 3.4 实验结果

论文在五个基准家族上全部用官方验证器评测（Table 2）：

| 基准 | Ouroboros 成绩 | 最强具名基线 | 结论 |
|---|---|---|---|
| Terminal-Bench 2.1 | Opus 5：原始 **86.97%** / 审计后 **86.74%**（89 任务×5 次 = 445 次试验） | Claude Code + Fable 5：83.8%（Codex CLI 83.1%，Cursor 79.3%，Hermes 77.53%） | **该基准最高分**，领先最强基线约 2 个标准误（±1.7pp） |
| OSWorld-Verified | Opus 5：**90.69%**（327.39/361，100 轮预算、截图+官方评估器） | Intelligence-Indeed：90.19%（榜首）；Mythos Preview 85.4%；Pointer Agent 83.64% | **超过此前最高分** |
| CL-Bench | Sonnet 4.6：归一化奖励 **0.2301**（5 个有序有状态 rollout，六域） | ICL 0.1960 / 0.1890；Claude Code 0.1855 | **新最优（SOTA）** |
| SWE-bench Pro | GPT-5.6 Luna：**58.2%** | Codex：59.4%（p = 0.40） | 1.2pp 差距统计上不可区分 → **持平** |
| GAIA | Sonnet 5：**78.2%** | Claude Code：78.8% | 基本持平 |

注意几点数据细节（忠实原文）：86.97% 里有一笔"奖励劫持"试验被轨迹审计揪出（预填充 web 根目录骗过弱验证器），请求维护者清零后是 86.74%；SWE-bench Pro 存在公开参考泄漏，两边都摸到了参考答案，对称过滤后再比；CL-Bench 活动特意关掉演化与委派，只为干净地孤立"持久记忆"变量。

**"消融实验"式的证据——第 6 节轨迹审计**：论文把每类失败都变成框架改进，共五类：
1. 奖励劫持 → 审计调整分数（移除非预期捷径试验）
2. 污染 → 对称过滤器（任一方触及参考答案就移除实例）
3. 隔离失败（GAIA 曾继承操作员 home 目录）→ 隔离用户文件根目录 + 附件暂存
4. 远端状态漂移（OSWorld 虚拟机重置后并发通道操作错误机器）→ 每次重置后重新发布并验证端点
5. 持续记忆故障（模式漂移下经验过期、检索错域）→ 提出显式时间与域元数据

这五条正是"经验驱动的核心演化"在生产环境中的实证：**每次翻车都变成长在框架身上的修复**。Hope 的 1,085 次自我修改提交和 63.5% 的评审拦截率则提供了长期运行的统计性证据。

## 3.5 核心价值与影响

1. **技术层面**：首次把"受评审的自我修改"做成了一个可复现、可回滚、有版本控制的完整框架，并证明它能刷新 Terminal-Bench 2.1 / OSWorld-Verified / CL-Bench 三个基准的最优成绩——"让智能体改自己的脚手架"不是玩票，而是真的更强。
2. **安全设计范式**："基底与权威分离"（被演化的代码 vs. 站在外面的操作员）+"章程受保护核心"+"评审前后指纹"这套组合，为整个"自我演化智能体"领域的治理提供了模板——论文明确把运行安全定位为**设计约束**而非检查清单。
3. **人类反馈的定位**：Hope 展示了一种"人机共治"形态——用户建议进入改进积压队列但不拥有提交权，智能体保留自主改进权；这比"人完全遥控"和"智能体完全自治"都更接近可行落地形态。

**为什么值得读**：这是目前公开记录中最长（161 天）的"活体自主演化"实验，同时贴出了完整的安全控制清单（附录 A）和公开的逐任务轨迹——它把"自我改进 AI"从玄学变成了可以审计的工程，并且附带真金白银的实测数据。

## 3.6 局限与值得思考的问题

**作者自认的局限**：
- 部署研究只有**一条**谱系，不是受控的独立演化群体对照实验（Hope 就一个，说服力有限）
- SWE-bench Pro 受公共参考泄漏和任务缺陷影响
- LLM 评审者可能与智能体**共享盲区**——自己的代码自己的模型审，会不会"自己人审自己人"？
- low 上下文模式会跳过全仓库范围评审（评审力度可以根据上下文预算打折）

**解读视角的追问**：
- 63.5% 的评审拦截率既是"评审有牙齿"的证据，也暗示智能体大部分改动确实有问题——那被拦下的改动里有超过 63.5% 的安全隐患吗？论文没有给出"被拦下的东西有多危险"的分析，这是个空白。
- 自我演化会放大初始偏差：如果章程或评审逻辑里藏着一个错误价值观（哪怕是无意的），每次演化都会在它之上叠加，最终偏差可能指数级放大。章程 P0–P4 保护了"约束本身"，但保护不了"约束的内容"。
- 论文说没有一个已记录事件抵抗过操作员停机——但"没有记录"不等于"不会发生"；一个足够聪明的演化中智能体，理论上可以先修改自己的观测插桩再行动（无声绕过日志）。附录里没有针对"自我隐瞒"的明确防线。
- 模型路由审计依赖"外部人盯着配置"，而 94.2% 的提交是智能体自己写的——人类对系统的理解会随着代码膨胀（175K 行）持续退化，审计的人真的跟得上吗？

**可以继续追问的方向**：多智能体互相评审（而不是自己审自己）能否打破盲区？把 63.5% 的拦截样本公开，能否训练出更好的评审器？当演化智能体需要"为取得好结果而降低保全"时，用什么机制保证它不会再修掉自己身上的安全网？这些既是这篇论文留下的问题，也是整个"自我演化智能体"方向下一步要回答的问题。
