## 摘要（Abstract）

大型语言模型（LLM）智能体日益承担长时程（long-horizon）任务，这类任务要求跨大量相互依赖的步骤进行持续的推理、工具使用与反复修改。然而，现有智能体框架（harness）将任务执行、任务状态与完成度评估都维护在同一个不断增长的上下文（context）中，这使得状态难以追踪，并允许错误的自我评估扩散进后续决策。我们将长时程执行重新表述为一个任务状态管理（task-state management）问题，并提出 LongHorizon-Harness：它在执行之外显式维护任务状态，并且仅用从环境中独立验证过的事实来更新它。其管理-执行-审计（Manage-Execute-Audit, MEA）循环使用一个管理者（manager）维护任务状态并确定下一个子任务，一个使用全新上下文（fresh-context）的执行器（executor）执行它，以及一个只读的审计器（auditor）在下一轮开始前验证所产生的环境状态。一个轻量级的 AgentAdapter 支持可互换的模型与框架后端，而不必修改它们的原生智能体循环。LongHorizon-Harness 在 WeaveBench 上将 Qwen 3.7-Plus 从 51.8% 提升到 80.7%，在 Terminal-Bench 2.1 上从 69.7% 提升到 77.2%，在 OSWorld 2.0 上从 2.8% 提升到 8.3%。它还将 Claude Opus 4.7 在一个 OSWorld 2.0 子集上从 20.0% 提升到 34.3%，展示了跨模型、跨框架与跨交互领域的一致提升。

## 1. 引言（Introduction）

在过去几年中，大型语言模型（LLM）已从对话模型演变为自主智能体的决策核心，广泛应用于软件工程（Yang et al., 2024; Wang et al., 2025; Ren et al., 2026; Ding et al., 2025）、通用助手（Anthropic, 2025; OpenAI, 2025a;b; Anthropic, 2026）、科学发现（Sun et al., 2025; Wei et al., 2025a）、计算机使用（Anthropic, 2024; OpenAI, 2025c; Google DeepMind, 2025; Sager et al., 2026; Zhou et al., 2026; Zheng et al., 2026）以及多模态交互（Zhang et al., 2023; Agashe et al., 2025）。在这些应用中，智能体日益面临长时程执行（long-horizon execution），它要求在大量相互依赖的步骤上进行反复的推理、工具使用、观察与修改，有时跨越多个上下文窗口或会话。智能体能够完成的任务长度越来越决定有多少工作可以委托给它。METR（Kwa et al., 2026）报告称，先进智能体的任务完成时程（task-completion horizon）大约每七个月翻一番，而对近期的模型该趋势加速到约四个月。前沿编码智能体已经能够在单个项目上持续数小时的工作（OpenAI, 2025a; Anthropic, 2025; Yang et al., 2026a）。然而，更长的时程本身并不能使执行变得可靠（Dong et al., 2026）。

长时程执行的困难不在于任何单个步骤，而在于如何在一长串相互依赖的动作中维持连贯的进展。跨系统与跨领域，有三个挑战持续出现：（i）**错误累积与目标漂移（Compounding errors and goal drift）**。早期动作或决策中的错误沿轨迹累积，扭曲后续选择，并逐渐使智能体偏离其原始目标（Sun et al., 2026）。（ii）**上下文腐烂（Context rot）**。随着交互历史的增长，相关信息变得越来越难以检索与使用，一旦上下文利用率越过某个临界阈值，智能体性能可能急剧下降（Liu et al., 2024; Hong et al., 2025）。（iii）**任务状态丢失（Task-state loss）**。没有准确且最新的任务状态（即需满足的需求、已完成的动作、产生的工件以及从环境中发现的事实），长时程任务难以完成，而智能体常常在整个任务执行过程中无法恢复、保留并更新这一状态。

大量的努力从模型与框架两侧强化了智能体。前沿模型持续扩大规模、扩展上下文窗口，并通过在大规模高质量数据上训练获得更强的编码与智能体能力（Wei et al., 2025b; Chu et al., 2026; Li et al., 2025; Ma et al., 2026; Ji et al., 2025; Yang et al., 2026b）。与此同时，Claude Code（Anthropic, 2025）、Codex CLI（OpenAI, 2025a）与 OpenClaw（OpenClaw Contributors, 2026）等智能体框架已成为围绕模型组织提示、工具使用、上下文管理与多步执行的标准系统层。对于长时程任务，这些框架已经支持规划、任务分解、工具使用，以及在隔离上下文中执行或审查工作的子智能体（subagents）。然而，现有框架仍面临两个结构性局限：（i）**任务执行与任务状态管理共享同一个不断增长的上下文**。智能体用同一个上下文既执行任务又维护任务状态，而不断增长的执行历史使任务状态越来越难以追踪。（ii）**任务执行与完成度评估仍然耦合**。智能体执行每个子任务后自行判断其是否完成，而错误的判断可能被记为任务状态的一部分，并作为后续决策的前提。

为了解决这些局限，我们提出 LongHorizon-Harness，一个将长时程执行组织为一系列"独立审计的任务状态转移"的框架。我们的核心思想是：将任务状态作为执行之外的一条显式记录来维护，仅用从环境中独立验证过的事实来更新它，并从当前记录与原始目标出发推导出每个下一个子任务。具体来说，LongHorizon-Harness 遵循如图 1 所示的管理-执行-审计（MEA）循环。管理者（manager）读取当前任务状态，并定义一个带有依赖、约束与验收标准的子任务。执行器（executor）在全新上下文中仅执行这个子任务，而只读的审计器（auditor）独立检查环境，以确定发生了什么变化、哪些已完成、哪些仍未满足（Zhuge et al., 2024; Zheng et al., 2023）。管理者根据审计结果更新任务状态并开始下一轮，而执行器的交互历史在每轮结束后被丢弃，因此跨任务保留的只有紧凑、已验证的任务状态。通过一个轻量级的 AgentAdapter，LongHorizon-Harness 保留了现有系统的原生智能体循环（Yao et al., 2023），并支持三个角色全部可互换的后端，涵盖 Claude Opus、GPT 与 Qwen 等模型，以及 Codex CLI（OpenAI, 2025a）、Claude Code（Anthropic, 2025）、OpenClaw（OpenClaw Contributors, 2026）与 Hermes Agent（Nous Research, 2026）等框架。

**图 2 概览** LongHorizon-Harness 通过重复的"管理-执行-审计"轮次处理一个长时程任务 T，如虚线框与编号流程 ❶–❸ 所示。管理者读取任务状态 S_i 并构造子任务契约 c_i，其中指定目标、验收标准、边界约束与相关的先前证据（❶）。管理者也可以通过 ask 路由请求用户信息或授权。被选中的 GUI 或 CLI 执行器在全新、有预算上限的上下文中执行子任务并修改环境（❷）。审计器通过只读工具独立检查产生的环境并产出审计报告 v_i（❸）。管理者在下一轮之前用 v_i 更新任务状态。

我们在三个近期长时程基准上评估 LongHorizon-Harness，即 WeaveBench（Li et al., 2026）、OSWorld 2.0（Yuan et al., 2026）与 Terminal-Bench 2.1（Merrill et al., 2026），它们共同覆盖跨界面协调、桌面工作流与有挑战性的命令行任务。在匹配的模型后端与评估协议下，LongHorizon-Harness 使用 Qwen 3.7-Plus 与 Claude Code 将 WeaveBench 的 PassRate 从 51.8% 提升到 80.7%，几乎是 Claude Opus 4.7 搭配 Claude Code 的官方最强报告结果 41.2% 的两倍。在 Terminal-Bench 2.1 上，它将 Qwen 3.7-Plus 的性能从 69.7% 提升到 77.2%。在完整的 OSWorld 2.0 基准上，它将 Qwen 3.7-Plus 的二值完成率从 2.8% 提升到 8.3%；在一个 34 任务子集上，它将 Claude Opus 4.7 的结果从 20.0% 提升到 34.3%。我们的贡献总结如下：

- 我们将长时程执行从单个不断增长的轨迹重新表述为一个任务状态管理问题。任务状态在执行之外被显式维护，仅用独立验证的事实更新，并用于在原始目标下确定每个下一个子任务。
- 我们设计了 LongHorizon-Harness，通过一个"管理-执行-审计"循环实现这一原则。在每一轮中，管理者根据当前任务状态定义一个子任务，执行器在全新上下文中执行它，审计器在管理者更新状态并开始下一轮之前独立检查环境。
- 我们在 WeaveBench、OSWorld 2.0 与 Terminal-Bench 2.1 上评估了 LongHorizon-Harness。使用 Qwen 3.7-Plus，它使 WeaveBench 的 PassRate 从 51.8% 提升到 80.7%，Terminal-Bench 2.1 从 69.7% 提升到 77.2%，OSWorld 2.0 二值完成率从 2.8% 提升到 8.3%，同时在使用 Claude Opus 4.7 时也带来一致提升。

## 2. 方法（Method）

### 2.1 概述（Overview）

给定一个长时程任务 T 与一个计算机环境，LongHorizon-Harness 通过一系列动态确定的轮次（rounds）而非单个持续增长的会话（session）来执行任务。该框架在任务执行之外维护一个显式的任务状态，并且仅用从环境中独立验证的证据来推进它。跨轮次保留的只有任务状态及其支持的审计报告；执行器的原始交互轨迹在每轮结束后被丢弃。图 2 提供了框架概览。

每一轮遵循一个管理-执行-审计（MEA）循环。设 S_i 表示第 i 轮开始时可用的任务状态，E 为环境状态集合，e_{i-1} ∈ E 为当前环境状态，V_{i-1} = (v_1, . . . , v_{i-1}) 表示累积的审计报告。管理者构造一个有界的子任务契约（subtask contract）c_i。一个全新上下文的执行器执行该契约，将环境从 e_{i-1} 变换到 e_i，并返回执行报告 o_i。随后一个独立的审计器通过只读工具检查 e_i 并产出审计报告 v_i。管理者在确定是否还需要另一轮之前，将 v_i 并入下一个任务状态 S_{i+1}。循环在以下情况终止：审计后的状态满足原始任务、没有允许的子任务能推进剩余需求、需要用户输入，或轮次预算耗尽。

### 2.2 管理者（Manager）

管理者拥有持久任务状态并决定任务应如何推进。它可以访问原始任务 T、当前任务状态以及所有累积的审计报告，但对计算机环境没有直接接口。它不能观察应用状态、检查工作区内容、调用 GUI 或 CLI 工具，也不能修改环境。它的决策完全基于任务状态与审计器记录的环境证据。

在第 i 轮之后，管理者更新任务状态并产生下一个控制决策：

$$(S_{i+1}, q_{i+1}, c_{i+1}) = \Phi_{\text{mgr}}(T, S_i, V_i) \tag{1}$$

其中 V_i = (v_1, . . . , v_i)，q_{i+1} 是 execute、done、blocked、ask 四者之一。仅在需要进一步执行时才返回契约 c_{i+1}。

**任务状态更新（Task-state update）**。任务状态是任务相关记录的结构化集合：需求（requirement）表示源自原始任务的目标或约束，工件（artifact）表示执行期间创建或修改的输出，事实（fact）记录后续轮次所需的环境信息。每条记录被标记为 completed、pending、blocked 或 untrusted，并保留支持其当前状态的审计证据引用。初始状态 S_1 由 T 构造，其需求标记为 pending。每轮之后，管理者将 v_i 中已验证的发现应用到 S_i 上，添加或更新相应记录，同时将未解决的记录适当地保持为 pending、blocked 或 untrusted。执行器的声明不会直接改变持久状态：只有得到干净审计证据支持时，记录才会被标记为 completed。

**下一子任务构造（Next-subtask construction）**。管理者比较 S_{i+1} 与原始任务，选择一个从当前状态可以推进的未解决目标，并检查其依赖与前置条件。然后它构造一个有界的契约 c_{i+1}，指定即时目标、验收标准、边界约束，以及与执行和验证相关的任务状态记录与先前审计报告。该契约根据其所需的主要环境变换被路由到 GUI 或 CLI 执行器。当审计后的状态在无未解决完整性违规的情况下满足 T 时，管理者返回 done；当没有允许的动作能推进剩余需求时返回 blocked；当进展需要用户信息或授权时返回 ask；否则返回 execute 并附带 c_{i+1}。

### 2.3 执行器（Executor）

执行器执行管理者选定的契约，并且是唯一被允许有意修改环境的角色。在第 i 轮，它接收原始任务 T、当前任务状态 S_i、子任务契约 c_i，以及契约引用的先前审计报告。它将环境从 e_{i-1} 变换到 e_i：

$$(e_i, o_i) = \Phi_{\text{exec}}(T, S_i, c_i; e_{i-1}) \tag{2}$$

其中 o_i 总结执行期间执行的动作、产生的状态、创建或修改的工件以及遇到的问题。报告 o_i 描述执行器的结果，但并不能证明契约已完成。

**全新上下文执行（Fresh-context execution）**。每次执行器调用都作为一次全新、有预算上限的回合（episode）运行，只包含为当前轮提供的信息。它不会收到先前轮次的原始交互轨迹。在回合内，执行器可以进行多轮规划、环境交互、观察与修改。回合结束时，其原始轨迹与内部推理被丢弃；只有 o_i 被转发用于审计。

**GUI 与 CLI 能力边界（GUI and CLI capability boundaries）**。GUI 与 CLI 执行器通过不同的环境接口运作。GUI 执行器获得面向屏幕的能力，如截图、点击、滚动与输入文本，并负责以应用和界面状态为中心的变换。CLI 执行器获得 shell 执行、文件编辑、编码与测试等能力，并负责以工作区、进程与程序状态为中心的变换。

框架只暴露分配给所选执行器角色的环境接口与工具集。除非由其配置显式提供，该角色之外的能力不可用。这在分离不同类别状态修改动作的责任的同时，允许管理者为每个契约选择适当的接口。

**后端执行（Backend execution）**。执行器通过一个通用的智能体适配器接口实例化。给定一个契约、一个角色特定的环境接口与一个执行预算，适配器将现有后端（如 Claude Code、Codex CLI 或 OpenClaw）作为一次有界的回合启动。后端保留其原生规划与工具使用循环，并且当这些能力由其分配的角色暴露时，可以正常调用 shell、编辑文件、编写代码、运行测试或与应用程序交互。框架不会取代后端的内部执行过程；它控制提供的上下文、可用工具、环境权限、执行预算与返回的报告。

### 2.4 审计器（Auditor）

审计器独立验证执行器产生的环境状态。执行结束后，它接收原始任务 T、任务状态 S_i、契约 c_i、契约引用的先前审计报告以及执行器报告 o_i。它不会收到执行器的原始交互轨迹或内部推理。审计器检查产生的环境 e_i 并产出：

$$v_i = \Phi_{\text{aud}}(T, S_i, c_i, o_i; e_i) \tag{3}$$

其中 v_i 被追加到持久审计历史，并在下一轮前返回给管理者。

**独立环境检查（Independent environment inspection）**。审计器从一个排除执行器原始交互轨迹与内部推理的全新上下文开始。它可以使用 o_i 来定位相关文件、窗口、日志、进程或其他输出，但通过独立地将产生的环境与 c_i 中的目标、验收标准与边界约束进行比较来确定完成度。GUI 审计器通过以观察为导向的交互检查应用与屏幕状态，而 CLI 审计器使用非变更命令与检查工具检查文件、元数据、日志、进程、测试与工作区状态。在两种情况下，审计结论必须由直接从环境获得的证据支持，而非执行器的完成声明。

**只读权限（Read-only authority）**。审计器在必要时可以改变其观察视角以进行检查，但不能修改任务相关的环境状态。它不能创建、编辑、覆盖、移动或删除受保护工件，不能执行改变状态的命令，也不能执行改变所检查结果的 GUI 操作。框架在整个审计过程中监控任务相关的工作区与工件状态；任何检测到的变更都被记录为完整性违规（integrity violation），由此产生的报告不能支持已完成的任务状态记录。

**审计结果构造（Audit-result construction）**。审计报告 v_i 记录三类发现。第一，它通过评估契约的验收标准，分配 complete、incomplete 或 blocked 的完成状态。第二，它通过检查工作区变更、工件有效性与来源（provenance）以及相关删除约束，分配 clean、suspect 或 violation 的完整性状态。第三，它记录检查所支持的任务状态更新，包括已验证的事实、支持性证据与剩余缺口。

审计器可以提议修改需求、工件与事实记录，但由管理者决定这些发现在 S_{i+1} 中如何被并入。因此，o_i 仍然是一份未经验证的执行摘要，而 v_i 提供了可能推进持久任务状态的、基于环境的证据。

## 3. 实验（Experiments）

### 3.1 实验设置（Experimental Setup）

**对比配置（Compared configurations）**。我们使用 Qwen-3.7-Plus 作为主要骨干模型，并额外评估 Claude Opus-4.7 以考察跨骨干模型的普适性。对于每个骨干模型，我们将原始的 Claude Code 评估框架（Anthropic, 2025）与 LongHorizon-Harness 比较，后者使用 Claude Code 作为其执行后端。除非另有说明，管理者、执行器与审计器使用相同的骨干模型实例化，确保对比反映的是任务状态管理的影响而非模型能力的差异。

**实现细节（Implementation details）**。LongHorizon-Harness 通过统一的 AgentAdapter 接口集成现有智能体后端。每个角色分配独立的执行预算：执行器每轮限制 1800 秒，而管理者与审计器都限制为 300 秒。我们设置 MEA 最大轮数 N_max = 25。

**基准与指标（Benchmarks and metrics）**。我们在三个覆盖互补形式长时程执行的近期基准上评估 LongHorizon-Harness。

WeaveBench（Li et al., 2026）包含 114 个要求在同一工作流内协调 GUI 与 CLI 交互的任务。我们遵循标准 WeaveBench 评估协议，对所有任务使用官方基准发布的定义、工作区、运行时资产与裁判模板。我们报告 PassRate（完全通过任务百分比）与 Overall（所有任务的平均得分）。此外，我们报告基准覆盖的八个领域各自的 PassRate。

OSWorld 2.0（Yuan et al., 2026）包含 108 个桌面工作流任务，人类完成时间中位数约 1.6 小时。我们使用官方 osworld-v2-2026.06.24 发布版及其标准基于 Docker 的 VM 基础设施。我们报告两个指标：Binary 与 Partial Accuracy。Binary Accuracy 仅在任务最终得分为 1 时计为成功，而 Partial Accuracy 是所有任务的平均得分。

Terminal-Bench 2.1（Merrill et al., 2026）旨在评估智能体在富有挑战性且现实的命令行任务上的表现。我们遵循 Qwen 系列模型所使用的评估设置，并使用 Harbor 搭配 Docker 后端在 Terminal-Bench 2.1 上评估。最终结果报告每个任务三次独立运行的平均分，并与官方排行榜结果比较。

### 3.3 分析（Analysis）

接下来我们考察这些收益的计算成本、它们出现的任务条件，以及模型与框架如何共同决定所产生智能体系统的能力。

**成本-性能权衡（Cost–performance trade-off）**。图 4 显示 LongHorizon-Harness 将 Qwen 3.7-Plus 移到 OSWorld 2.0 成本-性能前沿上一个明显更强的点。同一模型将二值完成率从 2.8% 提升到 8.3%、部分得分从 21.5% 提升到 35.2%，尽管其每任务平均输出 token 消耗从 28.9K 增加到 104K。这一结果表明，更强的框架可以提高固定模型可达到的任务级性能。使用 Qwen 3.7-Plus 观察到的成本增加是该模型-任务配置特有的；如下文分析，LongHorizon-Harness 的 token 成本在很大程度上取决于底层执行器的能力。

**跨角色的计算量（Computation across roles）**。图 5 将 LongHorizon-Harness 的 token 消耗分解到管理者、执行器与审计器。管理者在 WeaveBench、OSWorld 2.0 与 Terminal-Bench 2.1 上分别仅占总 token 的 2.8%、2.0% 与 8.1%，表明显式任务状态维护带来的计算开销很小。审计器分别占 token 的 19.4%、24.8% 与 38.1%，表明独立验证构成框架的主要额外投入。然而，总体 token 变化在不同基准上不同。LongHorizon-Harness 在 WeaveBench 上消耗基线 2.3 倍的 token，在 OSWorld 2.0 上消耗基线 3.6 倍的输出 token，而在 Terminal-Bench 2.1 上尽管取得了更高的成功率，token 消耗却减少了 24%。这些结果表明该框架并不施加固定的 token 乘数。其总成本既取决于任务，也取决于底层模型所需的执行与恢复轮次数。

**任务相关的有效性（Task-dependent effectiveness）**。图 6 比较了 LongHorizon-Harness 在不同任务类型上的收益。在 WeaveBench 上，Design 与 Spatial/3D 获得最大的 PassRate 提升，分别为 60.0 与 50.0 个百分点，而基线已到达 83.3% 的 Desktop 领域仅提升 5.6 个百分点。在 OSWorld 2.0 上，一些最大的提升出现在流式交互、人在回路与跟随教程类任务中。在 Terminal-Bench 2.1 上，系统管理与游戏任务大幅提升，而若干简短的分析类别的提升较小甚至出现回退。尽管通过不同接口运作，提升较大的类别普遍要求智能体在扩展的轨迹上保留、检查并修改多个相互依赖的环境状态。若干分析类别上较小的提升表明，当任务性能由单一模型能力（如视觉感知、数学推理、编码或算法设计）主导时，LongHorizon-Harness 的收益较小。独立审计可以检测到错误结果并发起恢复，但它无法提供模型本身不具备的能力。因此，LongHorizon-Harness 的有效性较少取决于任务使用 GUI 还是 CLI，而更多取决于其主要瓶颈在于长时程执行可靠性还是解决单个步骤。

**智能体能力是一种系统属性（Agent capability as a system property）**。表 4 在相同的 17 个 WeaveBench Games 任务上，使用 Claude Opus 4.7 与 Qwen 3.7-Plus 比较了 Claude Code 基线与 LongHorizon-Harness。LongHorizon-Harness 将 Opus 的平均分从 0.680 提升到 0.809，Qwen 从 0.524 提升到 0.733，最大的提升集中在对应基线表现差的任务上。Qwen 基线得分不高于 0.04 的全部六个任务恢复到了 0.30 到 0.92 之间的分数，表明该框架主要通过在原本几乎完全失败的轨迹上进行恢复来提高失败下限。搭配 LongHorizon-Harness 的 Qwen 平均分达到 0.733，超过了使用基础 Claude Code 框架的 Opus 所取得的 0.680。这一比较表明，智能体能力是整个模型-框架系统的属性。模型决定每个执行轮内可用的动作与解决方案，而框架决定这些局部能力被分解、验证、恢复与累积为端到端任务完成的可靠程度。因此，更强的框架可以提高固定模型可达到的任务级性能，即使它没有为该模型增加新的原语能力。token 结果揭示了同样的双重依赖：LongHorizon-Harness 将 Qwen 的平均消耗从每任务 10.7M 增加到 34.3M token，却将 Opus 的消耗从 16.5M 减少到 11.1M。这种相反的模式表明，更强的模型可以用更少的审计-重规划轮次满足子任务契约，而较弱的模型必须在重复执行与恢复上花费额外推理。模型能力与框架设计共同决定了长时程智能体可达到的性能与计算成本。

### 3.4 案例研究（Case Studies）

我们进一步比较配对轨迹：Claude Code 基线与 LongHorizon-Harness 使用相同的 Qwen 3.7-Plus 模型执行相同任务。这些案例考察在"管理-执行-审计"循环下轮次之间有什么得以保留。未解决的失败与已完成的进展被带到执行历史之外，完成声明在进入任务状态前被检查，未满足的依赖在管理者定义后续子任务时仍然可用。这些示例还说明了持久任务状态如何连接在各自全新上下文中运作的执行器。

**从停滞的交互中恢复（Recovering from a stalled interaction）**。图 7 比较了两个系统在相同的 GUI 交互失败后如何继续。基线识别出 Wireshark 的"Decode As"对话框无响应，但这个观察仍嵌在其不断增长的执行历史中。因此它回到同一交互超过 400 步，而没有收集剩余的任务证据。LongHorizon-Harness 则把失败的交互与未解决的证据缺口记录在任务状态中。后续执行器直接聚焦缺失的 simulcast 层图表与数据包级证据，将得分从 0.59 提高到 0.92。通过将停滞的交互外部化，LongHorizon-Harness 保留了已验证的进展，并只把未解决的需求交给下一个执行器。因此恢复从最新的审计任务状态继续，而非从产生它的失败轨迹继续。

**审计"看似完成"（Auditing apparent completion）**。图 8 展示了一个执行器在一个视觉上看似合理但未满足完整任务规格的结果处停下的案例。基线直接编辑文档 XML 并在标题看起来正确后终止。然而，任务要求样式通过 LibreOffice 工作流应用，因此结果得分为 0.00。LongHorizon-Harness 执行规定的 GUI 操作，在执行过程中确认样式更改，并逐页重新检查文档。随后审计器解析文档 XML，确认全部 15 个标题具有所需的底层样式，得到 0.89 的得分。这种独立审计阻止了执行器看似合理但不合规的完成声明成为持久任务状态的一部分。后续规划可以从环境中确认的文档状态出发，而非从执行器对自身结果的评估出发。

**保留修复前证据（Preserving pre-repair evidence）**。图 9 展示了一个任务，其中部分必需证据属于修复前的环境状态。基线捕获了公式错误的初始视图，但在完成完整的修复前证据序列之前就修改了电子表格。它的直接 XML 编辑在文件重新打开后仍留下公式错误，产生了不一致的前后记录。LongHorizon-Harness 将缺失的修复前证据记录为一个待处理需求。下一个执行器先完成这一证据，再修复电子表格并检查结果公式单元格。随后审计器审查完整的九张截图序列，将得分从 0.45 提高到 0.87。将修复前证据保持为显式状态，改变了从任务状态中选出的下一个子任务：原始电子表格状态在修复被允许修改它之前先被记录。由此产生的执行顺序在状态转移之间保留了前后一致的证据链。

**从已验证进展继续（Continuing from verified progress）**。图 10 比较了两条轨迹，模型都能完成核心优化，但差异在于剩余工作流如何被维护。基线改进了目标页面，但同一个不断增长的会话必须继续操作 DevTools、跟踪剩余交付物、收集证据并评估自身进展。反复的 DevTools 交互最终耗尽可用预算，使任务未完成。LongHorizon-Harness 将已完成的优化保留在任务状态中，并从剩余需求推导后续子任务。全新上下文的执行器随后确认页面状态、检查相关脚本结构并收集性能轨迹，而审计器检查最终截图与其元数据。得分从 0.53 提高到 0.85。因为已完成的优化持久保存在执行历史之外，后续执行器可以聚焦剩余证据，而无需重建或携带前面的优化过程。管理者在整个工作流中维持连续性，而每个执行器将其上下文用于当前环境变换，使模型的局部进展得以转化为更完整的任务结果。

## 4. 结论（Conclusion）

在这项工作中，我们提出了 LongHorizon-Harness，一个用于长时程智能体执行的通用框架，它通过"管理-执行-审计"循环将任务状态管理与环境交互分离。LongHorizon-Harness 将进展维护为显式、经审计的任务状态，在全新上下文中执行每个子任务，并跨轮次只携带独立验证的结果。在 WeaveBench、OSWorld 2.0 与 Terminal-Bench 2.1 上的实验显示，在混合 GUI–CLI 工作流、专业桌面任务、纯命令行环境与不同模型骨干上均有一致的提升。这些结果表明，长时程智能体能力不仅由底层模型决定，也由组织、验证并将其局部能力转化为端到端任务完成的框架决定。

## 附录 A 详细实验设置（Detailed Experimental Setup）

### A.1 WeaveBench

WeaveBench（Li et al., 2026）包含 114 个长时程计算机使用任务，覆盖八个领域：桌面应用（Desktop Applications）、文档处理（Document Processing）、游戏（Games）、Web 开发（Web Development）、数据分析与可视化（Data Analysis and Visualization）、DevOps、空间/3D 应用（Spatial/3D Applications）与设计（Design）。每个任务要求智能体在同一工作流内同时使用 GUI 与 CLI 交互，而非仅依赖命令行或浏览器操作。我们遵循标准 WeaveBench 评估协议：每个任务在隔离的容器化 Ubuntu 桌面虚拟机中启动，任务执行之间不共享运行时状态。任务定义、工作区、运行时资产、裁判模板与评分过程全部取自官方发布版。评估器使用 Claude Opus 4.7 作为轨迹感知裁判（trajectory-aware judge）。我们报告两个聚合指标：PassRate（得分不低于 0.8 的任务比例）与 Overall（全部 114 个任务的平均分）。除聚合结果外，我们还报告八个领域的领域级 PassRate：桌面应用（DSK）、文档处理（DOC）、游戏（GAM）、Web 开发（WEB）、数据分析与可视化（DAV）、DevOps（OPS）、空间/3D 应用（SPA）与设计（DES）。

对于模型与执行框架，我们评估 Qwen 3.7-Plus。Claude Code 运行时版本为 claude-code 2.1.76。每个任务最多允许 25 轮"管理-执行-审计"。每轮超时：执行器 1800 秒，管理者与验证器各 300 秒。任务侧 Claude Code 的推理投入（reasoning effort）设为 high；裁判使用 OpenClaw 执行，设置 AJ_THINKING=medium。

对于 GUI 工具，我们保留基本的 WeaveBench 计算机使用接口，包括截图感知工具与使用 pyautogui 实现的桌面执行工具，如 click、double-click、mouse move、keyboard input、scroll、drag 与 wait。此外，我们引入一个受限的证据保留工具 save_screenshot。该工具不提供任何新的环境控制能力，也不向智能体暴露额外信息；它只能将当前可见的真实桌面屏幕保存到目标目录，作为某些任务要求的官方截图工件。

由于 GUI 任务经常提供截图输入，我们对视觉输入使用图像 URL 代理：截图被上传到图床后端并在模型请求中作为图像 URL 引用，避免由多个 base64 编码截图导致的超大请求体。

### A.2 OSWorld 2.0

OSWorld 2.0（Yuan et al., 2026）包含 108 个专业桌面工作流任务，人类完成时间中位数约 1.6 小时。我们使用官方 osworld-v2-2026.06.24 发布版，包括相应的任务定义、任务资产、Docker 虚拟机镜像与模拟网站。实验使用标准 OSWorld 基于 Docker 的虚拟机基础设施，在 Ubuntu 桌面环境中进行，默认分辨率为 1920 × 1080。最终评分由原生 OSWorld env.evaluate() 过程执行。

与通常只依赖 GUI 动作的主要官方基线不同，LongHorizon-Harness 在 OSWorld-v2 上使用混合工具池。GUI 动作由虚拟机内的计算机 MCP 服务器执行，支持点击、键入、拖拽与快捷键等桌面操作。CLI 角色可以在同一虚拟机中执行 shell 命令，用于文件系统检查、脚本执行与长上下文任务处理。这些工具通过固定版本的 claude-code 2.1.176 托管在虚拟机内。

对于模型推理，我们设置 thinking.type=enabled、max_tokens=65,536、effort=max。原生 OSWorld 评估器与用户模拟器使用与执行智能体相同的 qwen3.7-plus 配置。对于基准中需要用户信息或授权的人在回路任务，我们不引入人工干预；而是使用原生 OSWorld 用户模拟器接口提供响应。

我们报告两个指标：Binary Accuracy 与 Partial Accuracy。Binary Accuracy 仅在任务最终得分为 1 时计为成功，而 Partial Accuracy 是全部 108 个任务的平均细粒度得分，衡量部分任务完成度。

### A.3 Terminal-Bench 2.1

Terminal-Bench 2.1（Merrill et al., 2026）旨在评估智能体在富有挑战性且现实的软件工程与命令行任务上的表现。我们使用 Harbor 作为评估框架，Docker 后端为每个任务提供隔离的执行环境。评估过程中，我们保留每个任务原先定义的 CPU、内存与环境约束。

为确保与现有 Qwen 系列模型评估的一致性，基线与 CUA-Harness 设置都使用 Claude Code 作为底层 CLI 执行智能体，连接 qwen3.7-plus 模型。Claude Code 版本为 v2.1.211。由于 Claude Code 命令行界面不直接暴露所有底层请求参数，我们在容器内引入一个透明的请求代理。所有模型请求配置为 temperature=1.0、top_p=0.95、top_k=20、enable_thinking=true、max_tokens=65,536。

每次试验超时 5 小时。我们对每个任务运行三次独立试验，报告每个任务三次运行的平均分，并与相同模型设置下的 Claude Code 基线以及官方排行榜结果比较。

#### B.2.1 WeaveBench

表 6 报告了 WeaveBench 的领域级分解。LH-Harness 在八个领域中的七个提升了平均分，最大提升在 Design（DES）、Spatial/3D Applications（SPA）与 Games（GAM）。通过率在包括 Desktop（DSK）在内的每个领域都有提升，尽管 DSK 的平均分略有下降而通过率更高。这一模式表明框架主要抬高了长时程轨迹的下尾：它将许多近乎失败转化为部分或完全成功，而少数已很强的基线轨迹可能受到额外验证与修复步骤的影响。

Games 领域提供了一个有用的压力测试，因为它结合了视觉交互、符号状态、搜索与环境特定约束。表 7 显示最大提升发生在基线常常无法建立稳定状态表示的任务上。例如，Mines、Stockfish puzzle analysis、Quadrapassel autoplay、PokerTH equity play 与 SuperTux level repair 都从接近零或零的基线得分提升到非平凡完成度。在这些案例中，框架通过将任务分解为显式子目标并携带验证过的事实而非长交互记录来提供帮助。相反，当基线已经解决核心任务时，额外轮次的收益较小甚至略微降低得分，如 rhythm autoplay、X-Moto、KMahjongg 与 FreeCell。

#### B.2.2 OSWorld 2.0

表 8 报告了按能力标签划分的 OSWorld 2.0 分解。标签不是互斥的，因此一个任务可能贡献于多个行。LH-Harness 提升了全部六个标签组，但幅度与残余失败模式差异显著。最大的提升出现在流式交互任务中，基线得分为零而 LH-Harness 平均达到 0.500。人在回路任务也大幅提升，表明框架受益于将用户提供的信息转化为持久状态约束。跟随教程任务提升，因为符号指令通常可以分解为带有明确验收标准的有界子任务。

标签级结果提示五个更具体的观察。第一，在人在回路任务中，主要收益来自将用户的响应视为持久约束而非短暂的对话轮次。同一机制也可能失败：如果新提供的信息没有覆盖陈旧证据，验证器可能确认一个过时的状态。第二，框架在跟随符号教程方面比具身教程更强。命令、表格、文件名与网页字段可以分解为可审计步骤；视频时间线、CAD 几何与精细鼠标操作仍然难以转化为可靠的低层动作。第三，当对环境状态存在权威闭合（authoritative closure）——如文件、数据库条目、应用设置或评估器可见工件——时，隐式状态推断效果最好。没有这种闭合，貌似合理的证据可能被误认为已完成的证据。第四，视觉任务的收益主要在视觉需求可以改写为文件、代码、元数据或搜索问题时出现。当需求仍纯粹是空间或运动层级时，性能仍受限于视觉定位与光标控制。第五，跨来源推理本身通常不是瓶颈。许多失败发生在相关证据已被理解之后：最终答案被写入错误的状态载体、保存在错误的边界，或没有通过预期接口提交。

#### B.2.3 Terminal-Bench 2.1

Terminal-Bench 提供了互补视角，因为大多数任务都是带隐藏测试的命令行任务。表 9 报告了类别级结果。最大提升在系统管理，LH-Harness 从 0.593 提升到 0.889。该类别以状态化流程为主，如安装、服务配置、PATH 管理、构建输出与持久环境副作用。这些正是显式任务契约与独立审计可以防止智能体在一段不完整但表面合理的命令序列后停下的场景。软件工程也大幅提升，尤其是在基线完成大部分工作但漏掉一个阻塞约束的任务中，例如图像相似度、异步取消行为、对参考二进制的独立性或压缩尺寸限制。

表 10 显示困难任务上的提升大于中等任务。这与框架的用途一致：当任务足够短、基线可以在单条轨迹内完成时，显式状态管理的边际价值较小。随着任务变长并包含更多中间失败点，记录未解决约束并从已验证状态重新规划的能力变得更加重要。

表 11 中的标签级结果进一步定位了效果。最强的正向标签是 images、version-control、system 与 sys-admin。这些标签有一个共同属性：正确性可以对照持久工件检查，如图像哈希或相似度分数、仓库历史、已安装可执行文件、服务状态、日志或文件系统布局。mteb、data-science 与 video-processing 等负向标签暴露了一个不同的局限。在这些任务中，官方正确性条件可能依赖于隐藏阈值、排名语义、时间定位或无法从可见状态完全恢复的评估约定。在这种情况下，LH-Harness 可能更仔细地组织执行，但误解的契约仍可能导致一个被自信验证的错误答案。

## 附录 C 更多案例研究（Additional Case Studies）

本附录以 WeaveBench 与 Terminal-Bench 的更多案例研究扩展第 3.4 节的定性分析。选择这些示例是为了说明支撑量化收益的同一机制：LongHorizon-Harness 不只是给模型更多动作，而是围绕显式任务状态、全新上下文执行与独立验证重构长时程执行。跨领域反复出现的模式是：局部执行进展只有在转化为可审计的状态命题后才变得有用——环境中发生了什么变化、它满足哪个需求、什么证据支持它、还有什么未解决。

**这些案例要说明什么（What the cases are meant to show）**。这些案例并非旨在孤立演示工具使用。相反，它们暴露长时程智能体的反复失败模式，并展示"管理-执行-审计"循环如何应对它们。第一，GUI 失败被外部化为未解决状态，而不是被困在不断增长的交互历史中。第二，工件不是因执行器声称完成而被接受；只有在只读审计器检查产生的环境后才被接受。第三，混合 GUI+CLI 执行让智能体使用最适合任务各部分接地（grounding）的界面：GUI 工具用于视觉与应用状态，CLI 工具用于文件、日志、元数据、构建产物与可复现性检查。最后，管理者将审计结果转化为下一个有界子任务，在保留已验证进展的同时避免上下文腐烂。

### C.1 跨领域 WeaveBench 案例（Cross-Domain WeaveBench Cases）

**桌面工作流：将 GUI 失败转化为验证过的状态转移（Desktop workflow）**。图 11 展示了 Joplin 中的桌面应用任务。任务要求创建一条富笔记、将其放入正确的笔记本，并复现一个标题栏渲染问题。关键点不在于执行器最终找到点击通过界面的方法。关键点在于失败的快捷键与不精确的点击被当作任务状态的变化：笔记正文已经存在，笔记本仍需创建，最终视觉 bug 仍需证据。LongHorizon-Harness 保留已验证的中间工件，将剩余 GUI 工作作为聚焦子任务路由，然后使用像素级截图比较来审计最终渲染差异。该案例说明了在不丢弃已完成工作、不信任执行器自我评估的情况下进行失败恢复。

**文档处理：验证语义文档状态而非视觉外观（Document processing）**。图 12 展示了一个文档编辑任务，其中标题的可见外观不足以作为完成证据。一个标题可以看起来又粗又大，但底层样式仍是错误的。LongHorizon-Harness 首先检查真实 LibreOffice Writer 状态，然后应用可复现宏来规范化标题，最后审计结果 ODT XML。这把一个视觉上貌似合理的编辑转化为一个可独立检查的命题：所有必需标题都以正确的标题样式与大纲级别编码。该案例强调为什么完成度必须基于环境状态而非截图或执行器的信心。

**游戏分析：结合 GUI 重放与文件级验证（Game analysis）**。图 13 展示了 XBoard 中的国际象棋分析任务。智能体必须识别一步非法走子并分析失败周围的局面。LongHorizon-Harness 使用 GUI 重放 PGN，直到 XBoard 本身在非法走子处停止，保留确切棋盘位置的视觉证据。然后它用生成报告的文件级检查补充 GUI 证据。结果是一个交叉验证的工件：非法走子、停止的棋盘状态、错着（blunder）分析与输出文件彼此一致。该案例展示了当 GUI 观察与文件检查单独都不够时混合执行的价值。

**Web 诊断：收敛浏览器图表、JSON 状态与数据包证据（Web diagnostics）**。图 14 展示了一个 WebRTC simulcast 层审计。任务要求识别一个层退化事件，并用浏览器与数据包捕获的证据支持它。LongHorizon-Harness 将工作流分离为产生证据的子任务：渲染浏览器图表、在相关时间戳悬停、捕获 tooltip 值，并打开 Wireshark 交叉检查 RTP 流。审计器随后将每张截图视为更大证据链中的一个命题，例如 f 层在目标区间附近降至每秒零帧。该案例说明框架如何防止冗长的 GUI 调查变成无结构的记录；每个观察都被记录为可指导下一步的验证事实。

**数据分析与可视化：审计证据质量，而不仅是文件存在（Data analysis and visualization）**。图 15 展示了一个 Airflow 调试任务。一个天真的轨迹可以用正确的文件名保存截图，却捕获错误的 UI 状态，例如在 Gantt 视图名称下保存 Grid 视图。LongHorizon-Harness 在审计期间检测到这种不匹配，阻止不合规截图支持完成，并分配一个聚焦的修复子任务来捕获真正的 Gantt 视图。它还交叉检查 DAG 图以识别不正确的上游依赖。关键教训是工件存在比工件有效性弱：一个文件存在只有在审计器确认其描绘了所需状态后才成为进展。

**DevOps：跨 UI 与 CLI 证据连接症状、根因与修复（DevOps）**。图 16 展示了一个 RabbitMQ 运维任务。表面症状在管理 UI 中可见：消息发布快于投递或确认。LongHorizon-Harness 随后结合 UI 检查与队列和绑定证据，识别出死信路由键不匹配。修复后，审计器对照 CLI 转储与管理 UI 截图交叉验证队列深度与绑定配置。这是一个典型的运维工作流：答案不是单个命令，而是一条从症状到根因到修复再到修复后证据的链条。

**空间与 CAD 工作流：通过视觉输出保留语义层（Spatial and CAD workflow）**。图 17 展示了一个 LibreCAD 任务。目标不仅是产出一个看起来合理的绘图，还要恢复语义层分配并生成可发布的视觉证据。LongHorizon-Harness 使用 CLI 渲染检查绘图确实存在，然后使用 LibreCAD GUI 检查并修复层属性，最后验证打印预览与保存的截图。审计器检查文件大小、分辨率、唯一性与时间戳顺序，确保提交的截图是不同状态的真实捕获而非回收的图像。该案例展示了 MEA 如何支持成功条件跨越结构化文件与视觉应用状态的任务。

**设计工作流：将主观视觉比较锚定在真实渲染状态（Design workflow）**。图 18 展示了一个基于 GIMP 的设计任务，涉及图像放大与质量比较。执行器不只是产生一个声称的结果。它在 GIMP 中打开实际输出，捕获 Levels 直方图，并排比较超分辨率与双三次（bicubic）结果，使用真实渲染管线生成证据。审计器随后可以评估视觉比较是否锚定在预期文件与应用状态中。该案例很重要，因为设计任务常包含看似主观的需求；LongHorizon-Harness 通过将它们转化为可复现、可检查的证据来提高其可靠性。

### C.2 Terminal-Bench 案例（Terminal-Bench Cases）

**构建与安装：使隐藏验收标准显式化（Build and installation）**。图 19 比较了基线与 LongHorizon-Harness 在一个 Terminal-Bench 任务上的表现，该任务要求使用 gcov 插桩编译 SQLite 并将结果放入 shell 环境。基线取得部分进展但未通过最终奖励，说明了一个常见的失败模式：智能体完成了大量工作却漏掉一个阻塞验收条件。LongHorizon-Harness 将任务转化为一个稳定契约，覆盖源码来源、构建位置、gcov 插桩、PATH 可见性、可执行性以及 vendored tarball 的保留。每轮审计该契约的一个子集，然后管理者才推进。最终交付物因此不仅是一个构建日志，而是一个经过验证的安装，其二进制、PATH 条目、gcov 符号与覆盖率文件都被独立检查。

**逆向工程：审计假设直到它们成为独立工件（Reverse engineering）**。图 20 展示了一个逆向工程任务，智能体必须产出一个独立的 C 程序，在严格约束下匹配一个神秘二进制的图像输出。该任务困难，因为早期观察是假设而非交付物：字符串、符号、像素统计与反汇编轨迹可以指导解决方案，但其中任何单独一项都不能证明完成。LongHorizon-Harness 将这些观察作为审计事实保留，然后用后续轮次综合、编译、压缩并对照原始行为测试最终程序。审计器不仅检查图像存在且可编译，还检查在移除原始二进制后生成的输出是否等价。该案例展示了 MEA 如何支持探索性任务：不确定的证据可以累积而不被误认为完成，最终状态只有在独立工件满足完整契约时才被接受。

### C.3 跨案例要点（Cross-Case Takeaways）

跨这些案例，LongHorizon-Harness 通过一个通用结构而非基准特定启发式提高可靠性。在文档与 CAD 任务中，它分离视觉貌似合理与语义正确。在 Web、数据分析与 DevOps 任务中，它在将进展标记为完成前强制不同界面的证据一致。在桌面与设计任务中，当 GUI 交互失败时它保留可恢复的中间工件。在 Terminal-Bench 任务中，它将隐式评分需求转化为显式验收契约并逐轮审计。这些模式支持论文的核心主张：长时程智能体性能不仅受模型局部能力限制，还受框架如何表示、验证并携带任务状态限制。
