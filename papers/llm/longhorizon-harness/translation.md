## 摘要（Abstract）

大语言模型（Large Language Model, LLM）智能体越来越多地承担长时程任务（long-horizon tasks），这类任务需要在大量相互依赖的步骤上持续进行推理、工具使用和修正。然而，现有的智能体执行框架（agent harness）把任务执行、任务状态（task state）和完成度评估都维护在不断增长（growing）的上下文之中，导致状态难以追踪，并允许错误的自我评估传播到后续决策中。我们将长时程执行重新表述为一个**任务状态管理问题**，并提出 LongHorizon-Harness：它在执行之外显式维护任务状态，并且只用从环境中独立验证过的事实来更新状态。其**管理-执行-审计**（Manage-Execute-Audit, MEA）循环使用一个管理者（manager）来维护任务状态并决定下一个子任务，一个使用全新上下文（fresh-context）的执行者（executor）来执行该子任务，以及一个只读的审计者（auditor）在下一轮开始前验证产生的环境状态。一个轻量级的 AgentAdapter 支持在不修改原生智能体循环的情况下互换模型与执行框架后端。LongHorizon-Harness 将 Qwen 3.7-Plus 在 WeaveBench 上从 51.8% 提升到 80.7%，在 Terminal-Bench 2.1 上从 69.7% 提升到 77.2%，在 OSWorld 2.0 上从 2.8% 提升到 8.3%；它还将 Claude Opus 4.7 在一个 OSWorld 2.0 子集上从 20.0% 提升到 34.3%，展示了跨模型、跨执行框架、跨交互领域的持续收益。

## 1. 引言（Introduction）

在过去几年中，大语言模型已经从对话模型演变为自主智能体的决策核心，应用于软件工程 [29; 26; 22; 6]、通用助手 [3; 19; 18; 4]、科学发现 [24; 27]、计算机使用 [2; 20; 8; 23; 37; 36] 以及多模态交互 [34; 1] 等领域。在这些应用中，智能体越来越多地面临**长时程执行**（long-horizon execution），它要求在大量相互依赖的步骤上进行反复的推理、工具使用、观察与修正，有时甚至跨越多个上下文窗口或会话。智能体能够完成的任务长度，越来越决定有多少工作可以委托给它们。METR [11] 报告称，先进智能体的任务完成时程大约每七个月翻一番，而近期模型该趋势已加速到约四个月。前沿编码智能体已经可以在单个项目上持续工作数小时 [19; 3; 30]。然而，更长的时程本身并不能让执行变得可靠 [7]。

长时程执行的难点不在于任何单独的一步，而在于如何在一长串相互依赖的动作中维持连贯的进展。跨系统和跨领域，有三个挑战持续出现：(i) **累积误差与目标漂移**（compounding errors and goal drift）。早期动作或决策中的错误会沿着轨迹累积，扭曲后续选择，并逐渐使智能体偏离其原始目标 [25]。(ii) **上下文腐化**（context rot）。随着交互历史不断增长，相关信息越来越难以检索和使用，一旦上下文利用率越过某个临界阈值，智能体性能可能急剧下降 [14; 9]。(iii) **任务状态丢失**（task-state loss）。没有准确且最新的任务状态（即需要满足的需求、已完成的动作、产出的工件以及从环境中发现的事实），长时程任务就很难完成，但智能体往往无法在整个任务执行过程中恢复、保留并更新这一状态。

大量的努力从模型侧和执行框架侧两方面强化了智能体。前沿模型继续扩大规模、扩展上下文窗口，并通过在大规模高质量数据上训练获得更强的编码与智能体能力 [28; 5; 12; 15; 10; 31]。与此同时，Claude Code [3]、Codex CLI [19] 和 OpenClaw [21] 等智能体执行框架已成为围绕模型组织提示词、工具使用、上下文管理和多步执行的标准系统层。对于长时程任务，这些框架已经支持规划、任务分解、工具使用，以及在隔离上下文中执行或审查工作的子智能体。然而，现有框架仍面临两个结构性局限：(i) **任务执行与任务状态管理共享同一个不断增长的上下文**。智能体用同一个上下文既执行任务又维护任务状态，而不断增长的执行历史使任务状态越来越难以追踪。(ii) **任务执行与完成度评估仍然耦合**。智能体执行每个子任务并自行判断其是否完成，一个错误的判断可能被记录为任务状态的一部分，并作为后续决策的前提。

为了解决这些局限，我们提出 **LongHorizon-Harness**——一个将长时程执行组织为一系列独立审计的任务状态转换的框架。我们的核心思想是：把任务状态作为执行之外的显式记录来维护，只用从环境中独立验证过的事实来更新它，并根据当前记录与原始目标推导出下一个子任务。具体而言，LongHorizon-Harness 遵循如图 1 所示的管理-执行-审计（MEA）循环。管理者读取当前任务状态，定义一个带有依赖、约束和验收标准的子任务；执行者在一个全新上下文中只执行这一个子任务；与此同时，一个只读的审计者独立检查环境，以确定什么发生了变化、什么已完成、什么仍未满足 [38; 35]。管理者根据审计结果更新任务状态并开始下一轮，而执行者的交互历史在每轮结束后被丢弃，使得整个任务中只有紧凑的、经过验证的任务状态得以保留。通过一个轻量级的 AgentAdapter，LongHorizon-Harness 保留了现有系统的原生智能体循环 [32]，并支持三个角色全部使用可互换的后端，覆盖 Claude Opus、GPT、Qwen 等模型以及 Codex CLI [19]、Claude Code [3]、OpenClaw [21]、Hermes Agent [17] 等执行框架。

我们在三个近期的长时程基准上评估 LongHorizon-Harness：WeaveBench [13]、OSWorld 2.0 [33] 和 Terminal-Bench 2.1 [16]，它们共同覆盖了跨界面协调、桌面工作流和富有挑战性的命令行任务。在匹配的模型后端与评估协议下，LongHorizon-Harness 使用 Qwen 3.7-Plus 和 Claude Code 将 WeaveBench 通过率（PassRate）从 51.8% 提升到 80.7%，几乎翻倍于由 Claude Opus 4.7 + Claude Code 取得的最佳官方结果 41.2%。在 Terminal-Bench 2.1 上，它使用 Qwen 3.7-Plus 将性能从 69.7% 提升到 77.2%。在完整的 OSWorld 2.0 基准上，它使用 Qwen 3.7-Plus 将二值完成率（binary completion）从 2.8% 提升到 8.3%；在一个 34 任务子集上，它使用 Claude Opus 4.7 将该结果从 20.0% 提升到 34.3%。我们的贡献总结如下：

- 我们将长时程执行从一条持续增长的轨迹重新表述为一个**任务状态管理问题**。任务状态在执行之外显式维护，只用独立验证过的事实更新，并用于在原始目标下决定每个下一个子任务。
- 我们设计了 **LongHorizon-Harness**，通过管理-执行-审计循环实现这一原则。每一轮中，管理者根据当前任务状态定义一个子任务，执行者在一个全新上下文中执行它，审计者独立检查环境，然后管理者更新状态并开始下一轮。
- 我们在 WeaveBench、OSWorld 2.0 和 Terminal-Bench 2.1 上评估了 LongHorizon-Harness。使用 Qwen 3.7-Plus 时，它将 WeaveBench 通过率从 51.8% 提升到 80.7%，Terminal-Bench 2.1 从 69.7% 提升到 77.2%，OSWorld 2.0 二值完成率从 2.8% 提升到 8.3%，同时使用 Claude Opus 4.7 也带来了一致的提升。

## 2. 方法（Method）

### 2.1 概述（Overview）

给定一个长时程任务 𝒯 和一个计算机环境，LongHorizon-Harness 通过一系列动态确定的轮次（rounds）来执行任务，而不是通过单个持续增长的会话。该框架在任务执行之外维护一个显式的任务状态，并且只用从环境中独立验证过的证据来推进它。跨轮之间，只有任务状态及其支撑审计报告得以保留；执行者的原始交互轨迹在每轮结束后被丢弃。图 2 给出了框架概览。

每一轮遵循一个管理-执行-审计（MEA）循环。令 Sᵢ 表示第 i 轮开始时可用的任务状态，eᵢ₋₁ ∈ ℰ 表示当前环境状态，Vᵢ₋₁ = (v₁, …, vᵢ₋₁) 表示累积的审计报告。管理者构造一个有界的子任务契约 cᵢ。一个使用全新上下文的执行者执行该契约，将环境从 eᵢ₋₁ 变换为 eᵢ，并返回一份执行报告 oᵢ。随后一个独立的审计者通过只读工具检查 eᵢ 并生成审计报告 vᵢ。管理者在决定是否还需要另一轮之前，将 vᵢ 纳入下一个任务状态 Sᵢ₊₁。当以下任一情况发生时循环结束：经审计的状态满足原始任务；没有任何允许的子任务能推进剩余需求；需要用户输入；或轮次预算耗尽。

### 2.2 管理者（Manager）

管理者持有持久的任务状态，并决定任务应如何进行。它可以访问原始任务 𝒯、当前任务状态以及所有累积的审计报告，但与计算机环境没有直接接口。它无法观察应用状态、检查工作区内容、调用 GUI 或 CLI 工具，也无法修改环境。它的决策完全基于任务状态和审计者记录的环境证据。

在第 i 轮之后，管理者更新任务状态并产生下一个控制决策：

$$(S_{i+1}, q_{i+1}, c_{i+1}) = \Phi_{\mathrm{mgr}}\left(\mathcal{T}, S_{i}, V_{i}\right) \tag{1}$$

其中 Vᵢ = (v₁, …, vᵢ)，qᵢ₊₁ 是 `execute`（执行）、`done`（完成）、`blocked`（受阻）和 `ask`（询问）之一。只有当需要进一步执行时，才返回契约 cᵢ₊₁。

**任务状态更新（Task-state update）。** 任务状态是任务相关记录的结构化集合：**需求**（requirement）表示源自原始任务的目标或约束，**产物**（artifact）表示执行期间创建或修改的输出，**事实**（fact）记录后续轮次所需的环境信息。每条记录被标记为 `completed`（已完成）、`pending`（待处理）、`blocked`（受阻）或 `untrusted`（不可信），并保留对其当前状态起支撑作用的审计证据的引用。初始状态 S₁ 由 𝒯 构造，其需求标记为待处理。每轮之后，管理者将 vᵢ 中已验证的发现应用到 Sᵢ，添加或更新相应记录，同时将未解决的记录适当保持为待处理、受阻或不可信。执行者的声称不会直接改变持久状态：一条记录只有在得到干净的审计证据支持时才会被标记为已完成。

**下一个子任务的构造（Next-subtask construction）。** 管理者将 Sᵢ₊₁ 与原始任务进行比较，选择一个可以从当前状态推进的未解决目标，并检查其依赖与前置条件。然后它构造一个有界的契约 cᵢ₊₁，规定直接目标、验收标准、边界约束，以及与执行和验证相关的任务状态记录和先前的审计报告。该契约根据其所需的主要环境转换被路由到 GUI 或 CLI 执行者。当经审计的状态在没有未解决的完整性违规的情况下满足 𝒯 时，管理者返回 `done`；当没有任何允许的动作能推进剩余需求时返回 `blocked`；当进展需要用户信息或授权时返回 `ask`；否则返回 `execute` 并附上 cᵢ₊₁。

### 2.3 执行者（Executor）

执行者执行管理者选定的契约，并且是唯一被允许有意修改环境的角色。在第 i 轮，它接收原始任务 𝒯、当前任务状态 Sᵢ、子任务契约 cᵢ，以及仅契约引用的先前审计报告。它将环境从 eᵢ₋₁ 变换为 eᵢ：

$$(e_{i}, o_{i}) = \Phi_{\mathrm{exec}}\left(\mathcal{T}, S_{i}, c_{i}; e_{i-1}\right) \tag{2}$$

其中 oᵢ 总结了执行期间执行的动作、产生的状态、创建或修改的产物以及遇到的问题。报告 oᵢ 描述了执行者的结果，但并不确立契约已经完成。

**全新上下文执行（Fresh-context execution）。** 每次执行者调用都以一个全新、有预算上限的情节（episode）运行，只包含为当前轮提供的信息。它不接收先前轮次的原始交互轨迹。在该情节内，执行者可以进行多轮规划、环境交互、观察与修正。当情节结束时，其原始轨迹和内部推理被丢弃；只有 oᵢ 被转发用于审计。

**GUI 与 CLI 能力边界（GUI and CLI capability boundaries）。** GUI 与 CLI 执行者通过不同的环境接口工作。GUI 执行者接收面向屏幕的能力，如截图、点击、滚动和输入文本，并负责以应用与界面状态为中心的转换。CLI 执行者接收 shell 执行、文件编辑、编码与测试等能力，并负责以工作区、进程与程序状态为中心的转换。

该框架只暴露分配给所选执行者角色的环境接口和工具集。该角色之外的任何能力都不可用，除非由其配置显式提供。这样既把不同类别的状态改变动作的责任分开，又允许管理者为每个契约选择适当的接口。

**后端执行（Backend execution）。** 执行者通过一个通用的智能体适配器接口实例化。给定一个契约、一个角色特定的环境接口和一个执行预算，适配器将现有后端（如 Claude Code、Codex CLI 或 OpenClaw）作为一个有界情节启动。后端保留其原生的规划与工具使用循环，并且当其角色暴露了相应能力时，可以正常调用 shell、编辑文件、编写代码、运行测试或与应用交互。该框架不替换后端的内部执行过程；它控制所提供的上下文、可用工具、环境权限、执行预算和返回的报告。

### 2.4 审计者（Auditor）

审计者独立验证执行者产生的环境状态。执行之后，它接收原始任务 𝒯、任务状态 Sᵢ、契约 cᵢ、契约引用的先前审计报告以及执行者报告 oᵢ。它不接收执行者的原始交互轨迹或内部推理。审计者检查产生的环境 eᵢ 并生成：

$$v_{i} = \Phi_{\mathrm{aud}}\left(\mathcal{T}, S_{i}, c_{i}, o_{i}; e_{i}\right) \tag{3}$$

其中 vᵢ 被追加到持久的审计历史中，并在下一轮之前返回给管理者。

**独立环境检查（Independent environment inspection）。** 审计者从一个排除执行者原始交互轨迹和内部推理的全新上下文开始。它可以使用 oᵢ 来定位相关文件、窗口、日志、进程或其他输出，但通过将产生的环境与 cᵢ 中的目标、验收标准和边界约束进行独立比较来确定完成度。GUI 审计者通过面向观察的交互检查应用与屏幕状态，而 CLI 审计者使用非变更命令和检查工具来检查文件、元数据、日志、进程、测试和工作区状态。在两种情况下，审计结论都必须由直接从环境获得的证据支持，而不是由执行者的完成声称支持。

**只读权限（Read-only authority）。** 审计者在必要时可以改变其观察视角以进行检查，但不能修改与任务相关的环境状态。它不能创建、编辑、覆盖、移动或删除受保护的产物，不能执行改变状态的命令，也不能执行会改变被检查结果的 GUI 动作。该框架在整个审计过程中监控与任务相关的工作区和产物状态；任何检测到的变更都会被记录为完整性违规（integrity violation），由此产生的报告不能支持已完成的（completed）任务状态记录。

**审计结果构造（Audit-result construction）。** 审计报告 vᵢ 记录三类发现。第一，它通过评估契约的验收标准来分配一个完成状态：`complete`（已完成）、`incomplete`（未完成）或 `blocked`（受阻）。第二，它通过检查工作区变更、产物有效性与来源，以及相关的删除约束，来分配一个完整性状态：`clean`（干净）、`suspect`（可疑）或 `violation`（违规）。第三，它记录检查所支持的任务状态更新，包括已验证的事实、支撑证据和剩余缺口。

审计者可以提议对需求、产物和事实记录的修改，但由管理者决定这些发现如何纳入 Sᵢ₊₁。因此，oᵢ 仍然是一份未经验证的执行摘要，而 vᵢ 提供基于环境的证据，可以用来推进持久任务状态。

## 3. 实验（Experiments）

### 3.1 实验设置（Experimental Setup）

**对比配置（Compared configurations）。** 我们使用 Qwen 3.7-Plus 作为主要骨干模型，并额外评估 Claude Opus 4.7 以检验跨骨干模型的通用性。对于每个骨干模型，我们将原始 Claude Code 评估框架 [3] 与 LongHorizon-Harness 进行比较，后者使用 Claude Code 作为其执行后端。除非另有说明，管理者、执行者和审计者都使用相同的骨干模型实例化，确保对比反映的是任务状态管理的作用，而非模型能力的差异。

**实现细节（Implementation details）。** LongHorizon-Harness 通过统一的 AgentAdapter 接口集成现有的智能体后端。每个角色被分配一个独立的执行预算：执行者每轮限制为 1800 秒，管理者和审计者均限制为 300 秒。我们设置最大 MEA 轮数为 N_max = 25。

**基准与指标（Benchmarks and metrics）。** 我们在三个覆盖互补形式的长时程执行的近期基准上评估 LongHorizon-Harness。

**WeaveBench** [13] 包含 114 个任务，要求在同一工作流内协调 GUI 与 CLI 交互。我们遵循标准 WeaveBench 评估协议，对所有任务使用官方基准发布的任务定义、工作区、运行时资源和判分模板。我们报告通过率（PassRate，定义为完全通过任务的百分比）和总体得分（Overall，定义为所有任务的平均分）。此外，我们还报告基准覆盖的八个领域中每个领域的通过率。

**OSWorld 2.0** [33] 包含 108 个桌面工作流任务，人工完成时间中位数约为 1.6 小时。我们使用官方 osworld-v2-2026.06.24 版本及其标准基于 Docker 的虚拟机基础设施。我们报告两个指标：二值准确率（Binary Accuracy）和部分准确率（Partial Accuracy）。二值准确率仅在任务最终得分为 1 时才将任务计为成功，部分准确率是所有任务的平均得分。

**Terminal-Bench 2.1** [16] 旨在评估富有挑战性且贴近现实的命令行任务。我们沿用 Qwen 系列模型所用的评估设置，使用 Harbor 搭配 Docker 后端在 Terminal-Bench 2.1 上进行评估。最终结果报告每个任务三次独立运行的平均得分，并与官方排行榜结果进行比较。

### 3.3 分析（Analysis）

接下来我们考察这些收益的计算成本、收益出现的任务条件，以及模型与执行框架如何共同决定最终智能体系统的能力。

### 3.4 案例研究（Case Studies）

我们进一步比较成对的轨迹，其中 Claude Code 基线和 LongHorizon-Harness 使用相同的 Qwen 3.7-Plus 模型执行相同的任务。这些案例考察在管理-执行-审计循环下，什么在各轮之间得以保留。未解决的失败和已完成的进展被携带在执行历史之外，完成声称在进入任务状态之前被检查，未满足的依赖在管理者定义后续子任务时仍然可用。这些例子还说明了持久任务状态如何连接在不同全新上下文中运行的执行者。

**从停滞的交互中恢复（Recovering from a stalled interaction）。** 图 7 比较了同一个 GUI 交互失败后两个系统的处理方式。基线识别出 Wireshark 的"Decode As"对话框无响应，但这一观察仍然嵌在其不断增长的执行历史中。结果它在超过 400 步的时间里反复回到同一个交互，却没有收集剩余的任务证据。LongHorizon-Harness 则将失败的交互和未解决的证据缺口记录在任务状态中。后续执行者直接专注于缺失的 simulcast 层图表和数据包级证据，将得分从 0.59 提升到 0.92。通过将停滞的交互外化，LongHorizon-Harness 保留了已经验证的进展，并只把未解决的需求交给下一个执行者。因此，恢复从最新的经审计任务状态继续，而不是从产生该状态的失败轨迹继续。

**审计表面上的完成（Auditing apparent completion）。** 图 8 呈现了一个执行者停在看起来合理、但并未满足完整任务规范的视觉结果上的案例。基线直接编辑文档 XML，并在标题看起来正确后终止。然而，任务要求通过 LibreOffice 工作流应用样式，因此结果得分为 0.00。LongHorizon-Harness 执行规定的 GUI 操作，在执行过程中确认样式更改，并逐页重新检查文档。随后审计者解析文档 XML，确认全部 15 个标题都具有所需的基础样式，得分 0.89。这种独立审计防止了执行者貌似合理但不合规的完成声称成为持久任务状态的一部分。后续规划可以转而从环境中确认的文档状态出发，而不是从执行者对其自身结果的评估出发。

**保留修复前的证据（Preserving pre-repair evidence）。** 图 9 呈现了一个任务，其中部分所需证据属于修复之前的环境状态。基线捕获了公式错误的初始视图，但在完成完整的修复前证据序列之前就修改了电子表格。其直接的 XML 编辑还在文件重新打开后留下公式错误，产生了不一致的前后记录。LongHorizon-Harness 将缺失的修复前证据记录为待处理需求。下一个执行者先完成这一证据，再修复电子表格并检查结果公式单元格。随后审计者审查完整的九张截图序列，将得分从 0.45 提升到 0.87。将修复前证据保持显式，改变了从任务状态中选择的下一个子任务：原始电子表格状态在修复被允许修改它之前就被记录。由此产生的执行顺序在状态转换中保留了一致性证据链。

**从经验证的进展继续（Continuing from verified progress）。** 图 10 比较了两条轨迹，模型都能执行核心优化，但维护剩余工作流的方式不同。基线改进了目标页面，但同一个不断增长的会话还必须继续操作 DevTools、跟踪剩余交付物、收集证据并评估自身进展。反复的 DevTools 交互最终耗尽可用预算，任务未完成。LongHorizon-Harness 将已完成的优化保留在任务状态中，并从剩余需求推导后续子任务。全新上下文的执行者随后确认页面状态、检查相关脚本结构并收集性能轨迹，而审计者对照元数据检查最终截图。得分从 0.53 提升到 0.85。因为已完成的优化存在于执行历史之外，后续执行者可以专注于剩余证据，而无需重建或携带前面的优化过程。管理者在整个工作流中维持连续性，而每个执行者将其上下文用于当前的环境转换，使模型的局部进展得以携带到更完整的任务结果中。

**图 7：从停滞的交互中恢复。** 案例为 WEB_task_16，一项 WebRTC simulcast 层审计。上：Claude Code 基线识别出 Wireshark 的"Decode As"对话框无响应，但继续重试同一个交互超过 400 步，得分 0.59。下：LongHorizon-Harness 将未解决的证据缺口记录在任务状态中。后续执行轮次收集缺失的图表级和数据包级证据，得分 0.92。

**图 8：审计表面上的完成。** 案例为 DOC_task_2，要求标题样式归一化。上：Claude Code 基线直接编辑文档 XML，以视觉上合理的结果终止。由于未遵循所需的 LibreOffice 工作流，得分为 0.00。下：LongHorizon-Harness 通过规定的 GUI 工作流应用标题样式并重新检查文档。随后审计者解析文档 XML 以确认全部 15 个标题的最终样式，得分 0.89。

**图 9：保留修复前的证据。** 在 DOC_task_4 中，智能体必须修复一个 Calc VLOOKUP 公式，同时保留前后证据。上：Claude Code 基线记录了初始公式错误，但在完成所需的修复前证据之前就编辑了电子表格，使最终文件和证据序列不一致，得分 0.45。下：LongHorizon-Harness 将缺失的修复前证据作为待处理需求保留，在修改前记录它，并审计完整的九张截图序列，得分 0.87。

**图 10：从经验证的进展继续。** WEB_task_10 是一个 Lighthouse 性能优化任务。上：Claude Code 基线完成核心优化，但在 DevTools 证据收集期间卡住，未能产出所有必需交付物，得分 0.53。下：LongHorizon-Harness 保留经验证的优化状态，将剩余证据需求委托给后续轮次，并审计最终截图与元数据，得分 0.85。

## 4. 结论（Conclusion）

在这项工作中，我们介绍了 LongHorizon-Harness，一个通用的长时程智能体执行框架，它通过管理–执行–审计循环将任务状态管理与环境交互分离。LongHorizon-Harness 将进展维护为显式的、经过审计的任务状态，在每个全新上下文中执行每个子任务，并跨轮只携带独立验证过的结果。在 WeaveBench、OSWorld 2.0 和 Terminal-Bench 2.1 上的实验显示，在混合 GUI–CLI 工作流、专业桌面任务、纯命令行环境和不同模型骨干上都有一致的改进。这些结果表明，长时程智能体能力不仅取决于底层模型，还取决于组织、验证并将其局部能力转化为端到端任务完成的执行框架。

## 附录 A 详细实验设置（Detailed Experimental Setup）

### A.1 WeaveBench

WeaveBench [13] 包含 114 个长时程计算机使用任务，覆盖八个领域：桌面应用（Desktop Applications）、文档处理（Document Processing）、游戏（Games）、Web 开发（Web Development）、数据分析与可视化（Data Analysis and Visualization）、DevOps、空间/3D 应用（Spatial/3D Applications）和设计（Design）。每个任务要求智能体在同一工作流中同时使用 GUI 和 CLI 交互，而不是仅依赖命令行或浏览器操作。我们遵循标准 WeaveBench 评估协议：每个任务在隔离的容器化 Ubuntu 桌面虚拟机中启动，任务执行不共享运行时状态。任务定义、工作区、运行时资源、判分模板和评分流程均取自官方发布。评估器使用 Claude Opus 4.7 作为轨迹感知判分器。我们报告两个聚合指标：通过率（得分至少为 0.8 的任务占比）和总体得分（全部 114 个任务的平均分）。除聚合结果外，我们还报告八个领域的领域级通过率：桌面应用（DSK）、文档处理（DOC）、游戏（GAM）、Web 开发（WEB）、数据分析与可视化（DAV）、DevOps（OPS）、空间/3D 应用（SPA）和设计（DES）。

对于模型和执行框架，我们评估 Qwen 3.7-Plus。Claude Code 运行时版本为 claude-code 2.1.76。每个任务最多允许 25 个管理-执行-审计轮次。每轮超时：执行者 1800 秒，管理者和验证者各 300 秒。任务侧的 Claude Code 推理努力设置为 high；判分器使用 OpenClaw 执行，AJ_THINKING=medium。

对于 GUI 工具，我们保留基础的 WeaveBench 计算机使用界面，包括截图感知工具和用 pyautogui 实现的桌面驱动工具，如点击、双击、鼠标移动、键盘输入、滚动、拖拽和等待。此外，我们引入了一个受限的证据保留工具 `save_screenshot`。该工具不提供任何新的环境控制能力，也不向智能体暴露额外信息；它只能将当前可见的真实桌面屏幕保存到目标目录，作为某些任务所需的官方截图工件。

由于 GUI 任务经常提供截图输入，我们为视觉输入使用图像 URL 代理：截图被上传到图像托管后端，并以图像 URL 的形式在模型请求中引用，避免多个 base64 编码截图导致的超大请求体。

### A.2 OSWorld 2.0

OSWorld 2.0 [33] 包含 108 个专业桌面工作流任务，人工完成时间中位数约为 1.6 小时。我们使用官方 OSWorld-v2 的 osworld-v2-2026.06.24 版本，包括相应的任务定义、任务资源、Docker 虚拟机镜像和模拟网站。实验使用标准 OSWorld 基于 Docker 的虚拟机基础设施，在 Ubuntu 桌面环境中进行，默认分辨率 1920 × 1080。最终评分由原生 OSWorld `env.evaluate()` 流程执行。

与通常只依赖 GUI 动作的主要官方基线不同，LongHorizon-Harness 在 OSWorld-v2 上使用混合工具池。GUI 动作由虚拟机内的计算机 MCP 服务器执行，支持点击、输入、拖拽和快捷键等桌面操作。CLI 角色可以在同一虚拟机内执行 shell 命令，用于文件系统检查、脚本执行和长上下文任务处理。这些工具通过固定版本的 claude-code 2.1.176 托管在虚拟机内。

对于模型推理，我们设置 thinking.type=enabled、max_tokens=65,536、effort=max。原生 OSWorld 评估器和用户模拟器使用与执行智能体相同的 qwen3.7-plus 配置。对于基准中需要用户信息或授权的人在回路任务，我们不引入人工干预；而是使用原生 OSWorld 用户模拟器接口提供响应。

我们报告两个指标：二值准确率（Binary Accuracy）和部分准确率（Partial Accuracy）。二值准确率仅在任务最终得分为 1 时才将任务计为成功，部分准确率是所有 108 个任务的平均细粒度得分，衡量部分任务完成度。

### A.3 Terminal-Bench 2.1

Terminal-Bench 2.1 [16] 旨在评估智能体在富有挑战性且贴近现实的软件工程和命令行任务上的表现。我们使用 Harbor 作为评估框架，Docker 后端为每个任务提供隔离的执行环境。评估期间，我们保留每个任务最初定义的 CPU、内存和环境约束。

为确保与 Qwen 系列模型现有评估的一致性，基线和 CUA-Harness 设置都使用 Claude Code 作为底层 CLI 执行智能体，连接到 qwen3.7-plus 模型。Claude Code 版本为 v2.1.211。由于 Claude Code 命令行界面不直接暴露所有底层请求参数，我们在容器内引入了一个透明的请求代理。所有模型请求配置为 temperature=1.0、top_p=0.95、top_k=20、enable_thinking=true、max_tokens=65,536。

每次试验超时为 5 小时。我们每个任务运行三次独立试验，报告每个任务三次运行的平均得分，并与相同模型设置下的 Claude Code 基线以及官方排行榜结果进行比较。

标签级结果提出了五个更具体的观察。第一，在人在回路任务中，主要收益来自将用户的响应视为持久约束而非短暂的对话轮次。同样的机制也可能失败：如果新提供的信息不能覆盖过时的证据，验证器可能确认一个过时的状态。第二，该框架在跟随符号化教程方面强于具身教程。命令、表格、文件名和网页字段可以分解为可审计的步骤；视频时间线、CAD 几何和精细鼠标操作仍然难以转化为可靠的底层动作。第三，当存在对环境状态的权威闭合（authoritative closure）——例如文件、数据库条目、应用设置或评估器可见的工件——时，隐式状态推断效果最佳。没有这种闭合，貌似合理的证据可能被误认为已完成的证据。第四，视觉任务的收益主要出现在视觉需求可以被重写为文件、代码、元数据或搜索问题的时候。当需求仍然是纯粹的空间或运动层面时，性能仍受限于视觉定位和光标控制。第五，跨来源推理本身往往不是瓶颈。许多失败发生在相关证据已被理解之后，当最终答案被写入错误的状态载体、保存在错误的边界，或没有通过预期的界面提交时。

## 附录 C 额外案例研究（Additional Case Studies）

本附录以 WeaveBench 和 Terminal-Bench 的额外案例研究扩展第 3.4 节的定性分析。这些例子旨在说明与定量收益相同的机制：LongHorizon-Harness 不只是给模型更多动作，而是围绕显式任务状态、全新上下文执行和独立验证重构长时程执行。跨领域反复出现的模式是：局部执行进展只有在被转化为可审计的状态命题后才有用——环境中发生了什么变化、它满足哪条需求、有什么证据支持它、还有什么未解决。

**这些案例要说明什么（What the cases are meant to show）。** 这些案例并非工具使用的孤立演示。相反，它们暴露了长时程智能体中反复出现的失败模式，并展示管理-执行-审计循环如何解决它们。第一，GUI 失败被外化为未解决的状态，而不是被困在不断增长的交互历史中。第二，产物不会因为执行者声称完成就被接受；只有在只读审计者检查产生的环境后才会被接受。第三，混合 GUI+CLI 执行让智能体使用最适合任务每个部分的界面：GUI 工具用于视觉和应用状态，CLI 工具用于文件、日志、元数据、构建产物和可复现性检查。最后，管理者将审计结果转化为下一个有界子任务，既保留经验证的进展，又避免上下文腐化。

### C.1 跨领域 WeaveBench 案例（Cross-Domain WeaveBench Cases）

**桌面工作流：将 GUI 失败转化为经验证的状态转换。** 图 11 展示了 Joplin 中的一个桌面应用任务。任务要求创建一条富文本笔记、将其放入正确的笔记本，并复现一个标题栏渲染问题。要点不在于执行者最终找到点击界面的方式，而在于失败的快捷方式和不够精确的点击被视为任务状态的变化：笔记正文已存在，笔记本仍需创建，最终视觉 bug 仍需证据。LongHorizon-Harness 保留经验证的中间工件，将剩余的 GUI 工作路由为聚焦的子任务，然后用像素级截图比较来审计最终的渲染差异。该案例展示了在不丢弃已完成工作、也不信任执行者自我评估的情况下进行失败恢复。

**图 11：桌面工作流案例。** LongHorizon-Harness 创建富文本笔记，通过更新任务状态从失败的 GUI 交互中恢复，并通过截图证据验证复现的渲染 bug。

**文档处理：验证语义文档状态而非视觉外观。** 图 12 展示了一个文档编辑任务，其中标题的可见外观不足以作为完成证据。一个标题可能看起来粗体且大号，但底层样式错误。LongHorizon-Harness 首先检查真实的 LibreOffice Writer 状态，然后应用一个可复现的宏来归一化标题，最后审计生成的 ODT XML。这将一个视觉上合理的编辑转化为可独立检查的命题：所有必需的标题都以正确的标题样式和大纲级别编码。该案例强调了完成度必须以环境状态为基础，而不能仅凭截图或执行者信心。

**图 12：文档处理案例。** 该框架验证底层 ODT 结构，而非依赖视觉格式，确保所有标题在语义上被归一化。

**游戏分析：将 GUI 回放与文件级验证结合。** 图 13 展示了 XBoard 中的象棋分析任务。智能体必须识别一步非法着法并分析失败周围的棋局状态。LongHorizon-Harness 使用 GUI 回放 PGN，直到 XBoard 本身在非法着法处停下，保留精确棋盘位置的视觉证据。然后用生成报告的文件级检查补充这一 GUI 证据。结果是一个交叉验证的工件：非法着法、停止的棋盘状态、漏招分析和输出文件彼此一致。该案例展示了当 GUI 观察和文件检查单独都不够时混合执行的价值。

**图 13：游戏分析案例。** GUI 回放识别非法的 PGN 转换，而文件级审计检查最终报告与棋盘证据一致。

**Web 诊断：汇合浏览器图表、JSON 状态和数据包证据。** 图 14 展示了一个 WebRTC simulcast 层审计。任务要求识别一个层降级事件，并用浏览器和数据包捕获的证据支持它。LongHorizon-Harness 将工作流分离为产生证据的子任务：渲染浏览器图表、悬停在相关时间戳、捕获悬停提示值，并打开 Wireshark 交叉检查 RTP 流。随后审计者将每张截图视为更大证据链中的一个命题，例如 f 层在目标区间附近降至每秒零帧。该案例展示了该框架如何防止冗长的 GUI 调查变成无结构的记录；每个观察都被记录为可指导下一步的经验证事实。

**图 14：Web 诊断案例。** LongHorizon-Harness 将浏览器图表、悬停提示证据和 Wireshark 检查组合成一条经审计的证据链。

**数据分析与可视化：审计证据质量，而非仅仅文件存在。** 图 15 展示了一个 Airflow 调试任务。一个天真的轨迹可以以正确的文件名保存截图，却捕获了错误的 UI 状态，例如在 Gantt 视图名称下保存了 Grid 视图。LongHorizon-Harness 在审计期间检测到这种不匹配，阻止不合规截图支持完成，并分配一个聚焦的修复子任务来捕获真正的 Gantt 视图。它还交叉检查 DAG 图以识别错误的上游依赖。关键教训是：产物存在比产物有效性弱——一个文件只有在审计者确认它描绘了所需状态后才成为进展。

**图 15：数据分析案例。** 该框架拒绝标签错误的证据，捕获正确的 Airflow 视图，并审计每张截图是否支持所需的诊断。

**DevOps：跨 UI 和 CLI 证据连接症状、根因与修复。** 图 16 呈现了一个 RabbitMQ 运维任务。表面症状在管理 UI 中可见：消息发布速度快于投递或确认速度。LongHorizon-Harness 然后将 UI 检查与队列和绑定证据结合，识别出死信路由键不匹配。修复后，审计者对照 CLI 转储和管理 UI 截图交叉验证队列深度和绑定配置。这是一个典型的运维工作流：答案不是单条命令，而是一条从症状、到根因、到修复、再到修复后证据的链条。

**图 16：DevOps 案例。** 该框架将管理 UI 症状与队列和绑定证据连接起来，然后跨 GUI 和 CLI 视图验证修复后的路由状态。

**空间与 CAD 工作流：通过视觉输出保留语义图层。** 图 17 展示了一个 LibreCAD 任务。目标不仅是产出一个看起来合理的绘图，还要恢复语义图层分配并生成可发布的视觉证据。LongHorizon-Harness 使用 CLI 渲染检查绘图确实存在，然后使用 LibreCAD GUI 检查和修复图层属性，最后验证打印预览和保存的截图。审计者检查文件大小、分辨率、唯一性和时间戳顺序，确保提交的截图是不同状态的真实捕获，而非重复使用的图像。该案例展示了 MEA 如何支持成功条件横跨结构化文件和视觉应用状态的任务。

**图 17：空间/CAD 案例。** 该框架结合 DXF 级检查、LibreCAD 图层修复、打印预览证据和截图完整性检查。

**设计工作流：将主观视觉比较锚定在真实渲染状态中。** 图 18 展示了一个基于 GIMP 的设计任务，涉及图像放大和质量比较。执行者不只是产出声称的结果。它在 GIMP 中打开实际输出，捕获 Levels 直方图，并排比较超分辨率与双三次结果，并使用真实渲染管线生成证据。审计者随后可以评估视觉比较是否锚定在预期文件和应用状态中。这个案例很重要，因为设计任务往往包含看起来主观的需求；LongHorizon-Harness 通过将它们转化为可复现、可检查的证据使其更可靠。

**图 18：设计案例。** LongHorizon-Harness 将视觉质量比较锚定在真实 GIMP 状态中，包括直方图和并排渲染输出。

### C.2 Terminal-Bench 案例（Terminal-Bench Cases）

**构建与安装：使隐藏的验收标准显式化。** 图 19 在 Terminal-Bench 任务上比较基线和 LongHorizon-Harness，该任务要求用 gcov 插桩编译 SQLite，并使结果在 shell 环境中可用。基线达到部分进展，但未通过最终奖励，说明了一个常见的长期失败模式：智能体做了大量工作，却遗漏了一个阻塞性验收条件。LongHorizon-Harness 将任务转化为一个稳定的契约，涵盖源码来源、构建位置、gcov 插桩、PATH 可见性、可执行性以及保留 vendor tarball。每一轮在管理者推进之前审计契约的一个子集。因此最终交付不只是构建日志，而是一个经过验证的安装，其二进制、PATH 条目、gcov 符号和覆盖率文件都被独立检查。

**图 19：Terminal-Bench 构建案例。** LongHorizon-Harness 将多条件构建任务转化为显式验收契约，并用 gcov 证据验证最终的 SQLite 安装。

**逆向工程：审计假设直到其成为独立工件。** 图 20 展示了一个逆向工程任务，智能体必须产出一个独立的 C 程序，在严格约束下匹配一个神秘二进制的图像输出。这个任务很难，因为早期观察是假设而非交付物：字符串、符号、像素统计和反汇编轨迹可以引导解决方案，但单独任何一项都不能证明完成。LongHorizon-Harness 将这些观察保留为经审计的事实，然后使用后续轮次综合、编译、压缩并对照原始行为测试最终程序。审计者不仅检查图像存在且可编译，还检查在移除原始二进制后生成输出仍然等价。该案例展示了 MEA 如何支持探索性任务：不确定的证据可以累积而不被误认为完成，并且只有当独立工件满足完整契约时最终状态才被接受。

**图 20：Terminal-Bench 逆向工程案例。** 该框架将探索性证据保留为经审计的事实，并对照行为、编译、大小和独立性约束验证最终的独立 C 实现。

### C.3 跨案例总结（Cross-Case Takeaways）

在这些案例中，LongHorizon-Harness 通过一个共同的结构而非基准特定的启发式来提高可靠性。在文档和 CAD 任务中，它区分视觉合理性与语义正确性。在网页、数据分析和 DevOps 任务中，它要求不同界面的证据在标记进展完成之前相互一致。在桌面和设计任务中，它在 GUI 交互失败时保留可恢复的中间工件。在 Terminal-Bench 任务中，它将隐式的评分要求转化为显式验收契约并逐轮审计。这些模式支持论文的核心主张：长时程智能体性能不仅受限于模型的局部能力，还受限于执行框架如何表示、验证和携带任务状态。
