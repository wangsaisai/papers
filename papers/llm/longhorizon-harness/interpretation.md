# LongHorizon-Harness 通俗解读

> 原文：LongHorizon-Harness: Advancing Long-Horizon Agents for Real-World Tasks（arXiv:2608.01964）
> 解读日期：2026-08-15

---

## 3.1 一句话总结

长任务拆成"派活—干活—验收"三班倒，只让独立验收过的进度入账，智能体少走弯路。

## 3.2 论文要解决的问题

**这个领域在干什么**：让大语言模型（LLM）智能体像人一样操作电脑完成任务——点界面、敲命令、改文件、查日志，一连干几小时，最终交出一个真实世界的成果（修好一个软件、生成一份报告、部署一项服务）。这类任务叫"长时程任务"（long-horizon tasks）：步骤多、互相依赖、中途要反复试错。

**为什么重要**：METR 的报告显示，智能体可持续完成的任务时程大约每 7 个月翻一倍（近期模型加速到约 4 个月），这意味着能"多长的活"越来越决定多少工作可以交给 AI。但**能撑得久不等于干得稳**——任务越长，中途出错、跑偏的概率越高。

**在这之前别人怎么做、哪里不够好**：现有主流方案（Claude Code、Codex CLI、OpenClaw 等智能体执行框架，harness）的思路是：让模型在一个**不断增长的会话**里，一边执行任务、一边记住任务进展、一边自己判断"我是不是做完了"。

这听起来自然，但有三个致命问题：

1. **累积误差与目标漂移**：早期的一步错会顺着轨迹滚雪球，把后面所有决策带偏，智能体慢慢忘了原始目标。
2. **上下文腐化（context rot）**：交互历史越来越长，相关信息淹没在噪音里，检索和使用都变难；上下文利用率一旦越过某个阈值，性能会断崖式下跌。
3. **任务状态丢失**：智能体常常记不住"还差哪些需求、已经做了什么、发现了什么事实"，状态一乱，长任务就完成不了。

> **类比**：想象一个新手厨师一个人开整个后厨——他一边炒菜，一边在自己脑子里记账（菜做到哪一步了、哪个客人忌口、调料还剩多少），还要一边自己尝菜判断"这盘菜能不能上"。刚开始还好，等到同时应付 20 桌菜，账本越来越乱，尝菜标准也越来越主观：一道菜他说"行了"，其实根本没按客人要求做。**记账、干活、验货全挤在同一个脑子里**，这就是现有框架的症结。

论文还指出现有框架的两个**结构性**局限（不只是"模型不够强"）：

- 任务执行和任务状态管理共用同一个不断增长的上下文——执行历史越长，状态越难追踪；
- 任务执行和完成度评估仍然耦合——智能体干了活、又自己给自己打分，**错误的自我评价会被当成事实记进状态，成为后续决策的前提**，一路错下去。

## 3.3 核心方法

**整体思路**：把"长时程执行"重新定义为"**任务状态管理问题**"。关键三步：把任务状态放到**执行之外**单独维护；只用**从环境中独立验证过的事实**更新状态；每轮根据当前状态+原始目标推导下一个子任务。核心机制是**管理–执行–审计（Manage-Execute-Audit, MEA）循环**。

> **类比**：这就像工程项目的"监理制度"。包工头（管理者）只看图纸和监理报告来派活，从不亲自抡锤子；工人（执行者）只负责干这一道工序；监理（审计者）只拿尺子量、拿仪器测，只写"合格/不合格"的报告，**没有监理签字，工作量不算数、不能记入台账**。一个工程被拆成一道道工序，每道工序干完先验收再进入下一道。

> （顺带一提：这个"管理-执行-审计"的 MEA 缩写和本工作区里 mea-coding skill 的"管理-执行-审计"工作流同名同构，都是"先定验收契约、小步执行、只读验证"的思路——工程实践和学术框架在这里撞了车，挺有意思。）

**三个角色各司其职**（论文的每个核心组件）：

**① 管理者（Manager）——管账和派活，不碰环境**
- 拥有持久的任务状态，能看到原始任务、当前状态、全部审计报告，但**没有**任何环境接口：不能看屏幕、不能点界面、不能执行命令。
- 每轮做两件事：**更新任务状态**（把审计报告里验证过的发现写进去），**构造下一个子任务契约**（cᵢ），契约写明：目标、验收标准、边界约束、相关先验证据。
- 决策四选一：`execute`（继续执行）、`done`（完成）、`blocked`（受阻）、`ask`（向用户询问）。
- 任务状态是结构化记录：**需求**（requirement，目标/约束）、**产物**（artifact，创建或修改的输出）、**事实**（fact，环境信息），每条记录标记为已完成/待处理/受阻/不可信，并**附上支撑它的审计证据引用**。
- 铁律：**执行者的自我声称不能直接改状态**——一条记录只有拿到干净的审计证据才能标记为"已完成"。

**② 执行者（Executor）——只干活，一次只干一件**
- 唯一被允许修改环境的角色，但每轮都在**全新上下文（fresh context）**里运行：只拿到本轮契约需要的材料，**看不到之前轮次的原始交互轨迹**。
- 一轮结束，原始轨迹和内部推理全部丢弃，只上交一份执行报告 oᵢ——注意，oᵢ 只是"执行者自称干了什么"，**不算完成证明**。
- **GUI/CLI 能力边界**：GUI 执行者只拿到截图、点击、滚动、输入等屏幕能力；CLI 执行者只拿到 shell、编辑、编码、测试等命令能力。谁也不能越界，但管理者可以按契约需要选合适的执行者。
- 执行者通过统一的 **AgentAdapter** 接口实例化：把 Claude Code、Codex CLI、OpenClaw 等现成后端"装进"一个有界情节里跑。后端保留自己的原生规划/工具循环，框架只控制上下文、工具、权限、预算和返回报告——**不重写任何现有智能体系统**。

**③ 审计者（Auditor）——只验收，只读权限**
- 独立检查执行者留下的环境：不看执行者的内部推理，从全新上下文出发，用只读工具自己查文件、日志、进程、屏幕状态。
- **只读权限**：不能创建/编辑/移动/删除受保护产物，不能跑改状态的命令，不能做改变被检查结果的 GUI 动作。任何被检测到的状态变更 = 完整性违规（integrity violation），该报告不能支撑"已完成"记录。
- 审计报告 vᵢ 三类发现：**完成状态**（complete/incomplete/blocked，对照契约的验收标准评估）；**完整性状态**（clean/suspect/violation，检查工作区变更、产物有效性、删除约束）；**任务状态更新建议**（验证过的事实、支撑证据、剩余缺口）。

**循环怎么转**（论文公式的通俗版）：

1. 第 i 轮开始时，管理者读状态 Sᵢ，产出决策 (Sᵢ₊₁, qᵢ₊₁, cᵢ₊₁) = Φ_mgr(𝒯, Sᵢ, Vᵢ)；
2. 执行者拿契约在全新上下文执行，环境从 eᵢ₋₁ 变到 eᵢ：(eᵢ, oᵢ) = Φ_exec(𝒯, Sᵢ, cᵢ; eᵢ₋₁)；
3. 审计者只读检查环境，产出 vᵢ = Φ_aud(𝒯, Sᵢ, cᵢ, oᵢ; eᵢ)，vᵢ 追加进审计历史并还给管理者；
4. 管理者用 vᵢ 更新状态，进入下一轮；循环结束条件：状态满足原始任务 / 没有合法子任务可推进 / 需要用户输入 / 轮数预算耗尽（默认最多 25 轮，执行者每轮 1800 秒、管理者和审计者各 300 秒）。

**三句话概括这个机制的妙处**：
- **跨轮唯一记忆 = 紧凑的审计报告**，不是越长越好的对话历史 → 治"上下文腐化"；
- **只有环境验证过的事实能入账**，执行者的自我评价永远只是"待验证声称" → 治"错误自我评估传播"；
- **每轮从最新经验证状态重新出发**，而不是从失败轨迹继续 → 治"累积误差和跑偏"。

## 3.4 实验结果

**在什么上验证的**：三个近期长时程基准——WeaveBench（114 个任务，同一工作流里要 GUI+CLI 协同）、OSWorld 2.0（108 个专业桌面工作流任务，人工中位耗时约 1.6 小时）、Terminal-Bench 2.1（硬核命令行任务）。主要骨干模型 Qwen 3.7-Plus，另测 Claude Opus 4.7 验证通用性。关键对照设计：**同模型、同执行后端，只差"是否套上 LongHorizon-Harness 的任务状态管理层"**，这样增量只能来自状态管理本身。

**主实验结果**（3.2 节，表 1/2/3、图 3）：

| 基准 | 配置 | 基线 → LongHorizon-Harness |
|---|---|---|
| WeaveBench | Qwen 3.7-Plus + Claude Code | 通过率 51.8% → **80.7%**，平均分 0.702 → 0.835（表 1） |
| OSWorld 2.0 | Qwen 3.7-Plus | 二值完成率 2.8% → **8.3%**（约 3 倍），部分得分 21.5% → 35.2%（表 2） |
| OSWorld 2.0 子集（34 任务） | Claude Opus 4.7 | 二值完成率 20.6% → **35.3%**，部分得分 55.8% → 66.9%（表 3） |
| Terminal-Bench 2.1 | Qwen 3.7-Plus + Claude Code | 成功率 69.7% → **77.2%**（图 3） |
| Terminal-Bench 2.1 | GPT-5.6 Luna + Codex 后端 | 达 **83.1%**（图 3） |

- WeaveBench 上 80.7% 几乎是官方最佳结果（Claude Opus 4.7 + Claude Code 的 41.2%）的两倍，且**八个领域全部提升**，说明收益不集中在某一类任务。
- **跨模型可迁移**：Qwen 和 Opus 都涨 → 不是"框架只救弱模型"；论文结论：模型定"每轮能想出多好的动作"，框架定"验证过的结果跨轮有多可靠"，两者互补（3.2 节"与骨干能力的互补性"）。

**分析/消融性质实验**（3.3 节，这是理解方法价值的关键）：

- **成本–性能**：OSWorld 上 Qwen 每任务输出 token 从 28.9K 涨到 104K（3.6 倍），WeaveBench 总 token 2.3 倍——多花钱换性能；但 Terminal-Bench 上 token **减少 24% 还涨分**。论文明确说"框架不施加固定 token 倍率"，成本取决于任务和模型（图 4、图 5）。
- **角色开销分解**（图 5）：管理者只占 2.8% / 2.0% / 8.1%（三个基准），**状态管理本身几乎零开销**；审计者占 19.4% / 24.8% / 38.1%，是主要额外投入——钱主要花在"验收"上。
- **任务类型消融式分析**（图 6、表 6/7/8/9/10/11）：收益最大的都是"需要长时间保存、检查、修正多个环境状态"的任务——WeaveBench 的 Design（+60.0 pp）、Spatial/3D（+50.0 pp）；OSWorld 的流式交互（+0.500）、人在回路（+0.332）；Terminal-Bench 的系统管理（+0.296）。**回退**集中在纯能力型任务：数据科学（-0.125）、数学（-0.167）、视频处理（-0.333）等——审计能发现错误并发起重做，但**不能凭空给模型它没有的能力**（视觉精度、数学推理）。
- **难度分层**（表 10）：困难任务 +0.122 > 中等任务 +0.042 → 任务越长、中间失败点越多，框架越值钱。
- **"智能体能力是系统属性"的关键证据**（表 4，17 个 Games 任务）：Qwen+LH 平均 0.733 **超过** Opus+Claude Code 的 0.680——更弱的模型+更强的框架能打赢更强的模型+更弱的框架；Qwen 基线 ≤0.04 的 6 个任务全部恢复到 0.30~0.92，框架主要"托底"（把近乎全败的轨迹救回来）。token 呈相反规律：Qwen 每任务 10.7M→34.3M，Opus 16.5M→11.1M——强模型用更少轮次就能过关，弱模型要靠多跑多验来补。
- **案例研究**（3.4 节，同模型同任务对比）：卡死的 Wireshark 对话框（基线 >400 步原地打转 0.59 → LH 0.92）；"看起来对"的文档样式（基线直接改 XML 拿 0.00 → LH 走正规工作流+审计 XML 拿 0.89）；修复前证据丢失（0.45 → 0.87）；DevTools 收集证据耗尽预算（0.53 → 0.85）。这四个案例分别对应"恢复停滞交互、拦截虚假完成、保留前后证据、从已验证进展继续"。

> 需要如实说明：论文**没有**做经典的"拆掉管理者/拆掉审计者"式逐组件消融；它的论证靠的是"同模型同后端、只差状态管理层"的匹配对比 + 按任务类型/角色开销的细粒度分解。对"三个组件各自贡献多少"没有给出量化拆解（解读视角：这是审稿人可以追问的点）。

## 3.5 核心价值与影响

1. **技术层面**：提出一个视角转换——长时程执行的本质问题是"任务状态管理"，并给出一个不依赖特定模型的通用实现（MEA 循环 + 显式任务状态 + 只读审计）。三个角色（管理/执行/审计）各自职责、能力边界和证据流转的定义都很清晰，公式 (1)(2)(3) 把循环形式化了。
2. **实用层面**：AgentAdapter 让框架能直接套在任何现有智能体上（Claude Code、Codex、OpenClaw……不用改它们的原生循环），开箱即用地把"同一模型"的基准分拉高一大截。对做 AI 电脑操作、软件工程智能体、办公自动化的团队，这是现成的工程模板。
3. **启发层面**：论文用数据论证了"**智能体能力 = 模型 × 执行框架**"的系统观——Qwen+LH 击败 Opus+CC 是全文最有力的一个反直觉结果。它提示后续研究：与其只卷模型，不如卷"如何组织、验证、累积局部能力"。附录 B/C 大量案例分析也为"什么样的任务适合状态管理"提供了分类学。

**为什么值得读**：如果你关心"AI 到底能不能可靠地独立干几小时的活"，这篇论文给出了一个简洁、可复现、跨三个主流基准都有效的答案——问题不全在模型，而在**状态怎么管、怎么验**。

## 3.6 局限与值得思考的问题

**作者在文中承认/暴露的局限**：

- 审计解决不了"模型本身没有的能力"：视觉定位、精细鼠标操作、数学推理等，框架只能检测错误并发起重做，不能凭空补能力（3.3 节、附录 B.2）。
- 验证器的盲区：当正确性条件依赖隐藏阈值（性能指标、排名语义、时序定位）或允许多种合理解释时，可能"自信地验证了一个错误答案"（附录 B.2.3）；人在回路任务里新信息若不覆盖旧证据，审计可能确认过时状态（附录 B.2.2）。
- 成本模型不固定：对弱模型/部分任务，token 消耗显著上升（OSWorld 3.6 倍）；收益集中在"瓶颈是长时程可靠性"的任务上，纯分析型任务可能回退。
- 部分任务有回退（如 Terminal-Bench 的数据科学、数学、视频处理类别），论文解释为"额外验证和修复步骤反而干扰了已很强的单步能力"。

**解读视角的补充观察**：

- **论文自身数字不一致**：摘要说 OSWorld 2.0 子集"20.0% → 34.3%"，但表 3 和附录 B.1 都写"20.6% → 35.3%"——两处口径不同，读原文时要注意（可能是摘要未更新）。
- **对比公平性的灰色地带**：WeaveBench 官方基线用普通用户账户，而本工作的运行在任务 VM 内使用 root 权限（表 1 注释）；OSWorld 上 LH 用的是"混合 GUI+CLI 工具池"，而官方基线通常只用 GUI 动作（附录 A.2）——提升有多少来自状态管理、有多少来自工具池扩展，论文没有完全剥离（作者自己标注了非匹配对比）。
- **没有真正的逐组件消融**（见 3.4 节末），且三个角色都用同一骨干模型，"审计者可信度"本身没有被独立检验——如果审计者模型不行，整个体系是否还成立？
- **可进一步追问**：审计者的"只读"权限在真实多用户系统里如何保证不误伤（检测变更的监控本身成本？）；状态记录会不会漏掉"难以形式化"的进度（比如感觉、审美）；25 轮上限和 1800 秒预算的敏感性如何；跨会话（断电/重启）恢复是否只靠任务状态文件就够了。
- **领域巧合**：论文的 MEA（Manage-Execute-Audit）与工程实践里的"先定验收契约、只读验证、小步推进"（本工作区的 mea-coding 工作流）思路同构，说明这套"管理-执行-审计"分工可能是长任务可靠性的通用处方。
