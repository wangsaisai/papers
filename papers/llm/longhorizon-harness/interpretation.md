# LongHorizon-Harness：推动长时程智能体应对真实世界任务（通俗解读）

> 论文：LongHorizon-Harness: Advancing Long-Horizon Agents for Real-World Tasks（arXiv:2608.01964，DreamX Team, Alibaba Group，2026-08-03）

## 3.1 一句话总结

把长任务拆成"规划-干活-独立验收"的小循环，让 AI 只带着经过验证的事实继续推进，任务成功率大幅提升。

## 3.2 论文要解决的问题

**问题是什么？** 现在的 AI 智能体（agent）已经能像人一样操作电脑完成任务，但遇到需要几个小时、几百步串联的"长时程任务"时，经常会做一半就乱了套：要么跑偏，要么卡死，要么自我感觉良好地交出一个错的成品。

**为什么重要？** 一个智能体能持续干活多久，直接决定我们能放心把多少工作交给它。METR 机构的报告显示，前沿智能体的"任务完成时程"大约每 7 个月翻一番，最近甚至加速到 4 个月。工业界已经出现能连续干几小时活的编码智能体（Claude Code、Codex 等）。但跑得久 ≠ 跑得稳——长长的轨迹上有无数个出错点。

**之前的方法有什么不足？** 现有智能体框架（Claude Code、Codex CLI 等）确实支持规划、拆解、工具调用，但有两个结构性问题：

1. **执行和记账共用一个大脑**：AI 一边干活，一边在同一个"记忆"（context）里记录"干到哪了"。对话记录越长，越难找到关键信息——就像你在一堆越来越厚的会议纪要里找上次讨论的结论。
2. **干活的自己给自己打分**：AI 做完一个子任务后自己判断"我做完了"，这个"自我评估"可能出错，但错误判断会被当成事实进入后续决策，一路错下去。

**类比**：就像一个人装修房子，既是工人又是监工又当验收员，一边干活一边把所有细节记在脑子里，干到第 300 步时脑子早乱了——忘了卫生间墙砖贴没贴、开关装没装，还坚信自己全干完了。

## 3.3 核心方法

**核心思想**：把"干活"（执行）与"管账+验收"（状态维护+审计）彻底拆开。长时程执行本质上是一个**任务状态管理问题**：谁可靠地记录"现在完成了什么、还差什么"，谁就决定了长任务能不能走完。

这就像把一个人装修变成**工头 + 工人 + 质检员**的流水线。LongHorizon-Harness 的"管理-执行-审计"（MEA）循环：

1. **管理者（Manager）= 工头**：不碰电脑，只看账本（任务状态）和质检报告，决定下一步干什么，写出"子任务契约"（目标、验收标准、边界、相关证据），并更新账本。
2. **执行器（Executor）= 工人**：只干这一件具体活，每次开工都用**全新干净的记忆**（fresh context），干完交个工作报告就失业注销——它的原始对话记录全部丢弃，不留给下一轮。
3. **审计器（Auditor）= 质检员**：用**只读权限**独立检查环境（不能改任何东西），对着"契约"验收"：完成没？干净没？变更有没有破坏别的？产出"审计报告"（证据），交给管理者记入账本。执行器说自己干完了没用，只有质检员的话才算数。

关键规则：

- **只有审计过的真凭实据才能更新账本**。执行器"我搞定了"的自我声明一律不算数（防自我评估扩散）。
- **跨轮传递的只有账本和审计报告**。每次工人开工都是"失忆"的，只带工头给的单子——从根源上杜绝上下文腐烂。
- **一个"AgentAdapter"适配器**把所有环节接到现有系统（Claude Code、Codex CLI、OpenClaw、Hermes 等），自家的原生智能体循环原封不动，模型（Qwen/GPT/Claude）可随意替换。
- 循环终止条件：验收全部满足 → done；没活干不动 → blocked；需要用户信息/授权 → ask；轮数用尽（默认最多 25 轮）→ 停。

**类比补充**：它就像给 AI 装了一个"**工程变更单系统**"——每一轮改动都先写变更单（契约）、施工、再由一个没有动手的人（质检员）核对现场后才销账，绝不会因为"我自己觉得完成了"就归档。

## 3.4 实验结果

在三个长时程基准上，用同一模型、同一执行后端做"有无此框架"的严格对比：

| 基准 | 指标 | 基线（Claude Code 直接跑） | +LongHorizon-Harness |
|---|---|---|---|
| WeaveBench（114 个 GUI+CLI 混合任务） | PassRate | 51.8% | **80.7%**（约翻倍，超过官方最强 Claude Opus 4.7 的 41.2%） |
| Terminal-Bench 2.1（纯命令行） | 成功率 | 69.7% | **77.2%** |
| OSWorld 2.0（108 个桌面工作流） | 二值完成率 | 2.8% | **8.3%**（约 3 倍） |
| OSWorld 2.0 子集（34 任务） | 二值完成率 | 20.6%（Opus 4.7） | **35.3%** |

其他要点：

- **换更强模型也有增益**：Claude Opus 4.7 在 34 任务子集上从 20.0% → 34.3%，证明不是"捡弱模型的漏"，而是两个模型的互补收益都有效。
- **成本不固定**：token 消耗在 WeaveBench 上为基线 2.3 倍、OSWorld 3.6 倍，但 Terminal-Bench 上反而**减少 24%**——所以不是"多烧钱换成绩"，模型越强、恢复轮越少。
- **审计是主要开销但不多**：管理者只占 2%~8% 的 token；审计占 19%~38%，是框架的主要投资。
- 消融式分析显示：**提升集中在长时程可靠性是瓶颈的任务**（设计、3D、游戏、系统运维等）；而瓶颈在"单步能力"的任务（视觉、数学推理、数据科学）收益很小甚至回退——因为审计器能抓错误、发补救，但没法凭空给模型新能力。
- 案例展示：600 步卡死在"Decode As"对话框的基线上，框架把失败记入账本后下一轮直接绕开，分数 0.59 → 0.92；直接改 XML 会被判 0 分的取巧操作，被审计器抓到后按正规流程走 GUI 得到 0.89。

## 3.5 核心价值与影响

1. **重新定义问题**：把长时程执行从"单条流轨迹"重新表述为"**任务状态管理**"，一切进展都必须先变成"被环境验证过的事实"，这为社区提供了统一的理论视角。
2. **可落地的工程框架**：不训练模型、不替换现有智能体，只通过 Adapter 包一层"管理-执行-审计"，高度可即插即用，并已开源（GitHub: AMAP-ML/LongHorizon-Harness）。
3. **"智能体能力是系统属性"**：用数据说明了能力 = 模型 × 框架，框架决定"局部能力被分解/验证/恢复/累积成端到端完成"的可靠性。一个更强的框架可以把同模型的成绩顶上去（Qwen 挂框架后 0.733 > Opus 挂裸框架的 0.680）。
4. **以后设计 agent 系统的共识坐标**：无论模型多强，"执行-记账-验收分离、跨轮只传证据"都会成为长时程任务的标准操作范式。

一句话：**值得读，因为它是"长时程智能体"领域第一个把任务状态管理做成独立系统层、并在三大基准上大幅提分的工程实证。**

## 3.6 局限与值得思考的问题

- **验证能力的天花板**：审计器自己也是 LLM，而且在必须可验证状态（文件、截图、元数据）的任务上才"照"得住。论文自己承认：视觉/运动精度、视频时间线、隐藏阈值类任务仍难闭合——审计器会把一个"被自信地验证过的错误答案"交出来。
- **契约枢纽风险**：管理者与审计器都是单点。若契约制定者（经理）把验收标准理解偏了，后面所有轮次的"精确审计"只会让错误更精致（B.2.3 节 mteb/data-science 类回退即是证明）。
- **评估的公平性存疑点**：WeaveBench 对比中 LongHorizon-Harness 使用了根权限，而官方基线是普通用户权限（自己承认并列入"参考而非严格对照"）；OSWorld 上是混合工具池对官方单动作模式。这些设置差异会影响结论的干净程度。
- **成本结论雾里看花**：token 倍率差异跨度巨大（-24% ~ +3.6×），对预算敏感的实际部署，需要针对自身任务单独测算。
- **可追问的方向**：审计器可不可能被复用/蒸馏成轻量模型？能不能让审计器也查验自身证据链的完整性？当任务时长以"天"计时、跨会话持久化时，账本要不要落盘成文件？状态与"验证成本"之间是否存在最优轮次切割？
